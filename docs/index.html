Run a software project as a graph of gated work. Prove the rules in code.

You write a row in a queue. Reef plans it with you, builds it in parallel in isolated worktrees, has a fresh context verify every task, opens the pull request and closes the row. You approve the plan and you merge the release; everything in between is decided by code, not by a prompt.

  • 3 It resumes from disk after /clear

Pick your situation. One command each.

The same rows as the README's install table, one at a time. Every command below is a Claude Code slash command inside your project.

A new project

/reef-init

One batched question set. Your branches, and the architecture grill: host, shape, scale, store, auth boundary, one-year non-goals.

What happens. Reef renders one tree adapted to your stack: .reef/config.json (every number, once), AGENTS.md, the constitution, the queue with row 1 = the walking skeleton, the architecture with draft decisions, the journal, glossary and day-zero list, a release-only CI, the git hooks, every scripts/reef-*, and reef/README.md, the map of the tree.

Idempotent: a second run with nothing changed writes nothing.

An existing project

/reef-init
/reef-assess

Nothing you wrote is overwritten. A differing rendering lands in .reef/proposed/<path> with a diff; apply the ones you choose:

python3 scripts/reef-init.py --accept <path>

What happens. /reef-assess reads how the project works, was written and was pushed, with every claim Observed with a proving path or Inferred. It scores how well a harness can hold the project, then recalibrates its documents into the tree under one batched approval.

Archive, never delete. Undo with one git revert.

A feature to build

/reef-plan <row>→/reef-task <slug>→/reef-review <slug>

Three commands and one question for you, asked last, after the machines have reviewed the plan: Approve plan <slug> at <digest16>?

What happens. The grill; a lean planner drafts the spec and the tasks in the feature's worktree; the hunter and a fresh reviewer read the draft in parallel; then the gate. Nothing after your approval voids it. Every ready task at once, each in its own worktree, each verified by a fresh judge. The PR, the proofs re-run, the hunter once on the whole diff, the acceptance against the spec, the merge and the close.

Each stage is explained in How it works.

A queue of rows

/reef-loop

The outer graph: every ready row through the three feature commands, in parallel where rows do not collide.

What happens. The loop stops only for your decisions, a missing credential, a wrong spec, or a cap. Its questions are batched. State lives on disk, so a new session reads the handoff head and one tick and continues every row from its last completed step; the tick names the next command and the files behind every id.

Without a gh-authenticated forge, Reef stops with USER ACTION REQUIRED and says exactly what it would have run.

Something looks off: /reef-doctor is one screen: the plugin clone's branch and freshness, scripts behind the plugin, the queue's home, worktrees, the loop's state, gh, Docker, waiting proposals, each with the command that fixes it.

A night delegated to Mahmoud (super Reef): /reef-night agrees tonight's rows, the decisions your proxy may take and the hard limits; you approve once, then python3 scripts/reef-run.py --night works while you sleep. Every decision is recorded as Mahmoud's; the morning report lists them apart from the merges.

A batch without restarting sessions: python3 scripts/reef-run.py probe once per machine, then python3 scripts/reef-run.py runs /reef-loop in fresh headless sessions one after another; at the context ceiling the next session takes over from the handoff. It stops when the loop needs you (your questions land in .reef/questions.md; the next interactive /reef-loop asks them as one set), stops, parks, or hits the iteration cap. One orchestrator per project: never beside an interactive loop.

The running app attacked: /reef-pentest <url> sends one adversary against every row of the threat model on a live copy of the app, the way a user or a logged-in attacker could; each hole becomes a found row in your queue. On demand, at any point; needs /reef-threat first; only a target you own.

Build without the loop, or check a new machine: /reef-graph is the build step /reef-loop already uses for every fresh task (graph mode, chosen automatically). Run it yourself only without the loop, or once on a new machine to run its probe. Never next to a running loop.

A new Reef: reef-update.py --commit pulls the plugin, refreshes your project's copies, commits Reef's own files and prints the two reload commands.

A fresh clone: make setup. Hooks are local git config and do not survive a clone.

How it works

From a queue row to a merge, seven stages. Click one.

You decide twice in the whole run: you approve the plan, after the machines have reviewed it, and you merge the release. Everything else is decided by code on state the agent cannot write. A dark dot marks a stage where you decide.

01 · The queue row you write it

Your backlog is reef/queue.md: one row per feature, with an id, what it depends on, a source (planned, or found along the way) and a batch number. The queue lives in one place, on your base branch in the main checkout, so every session sees the same list. Rows are edited by command: add-row, footnote, set-depends, and triage for found rows that went stale.

What you write

A sentence and a batch number. /reef-init seeds row 1 with the walking skeleton, the thinnest end-to-end slice of your project.

What lets it through

The row is in the current batch and every row it depends on is closed. A found row whose fix is one file in no risk class gets one light task and no ceremony.

Your part

Write the rows. Nothing starts until a row is ready.

02 · /reef-plan: grill, draft, machine review

Reef grills you once about the row. A lean planner then drafts the feature folder in the feature's own worktree: a spec with keyed requirements, one decision record with a diagram, and small vertical-slice tasks, each with at most plan.max_acs criteria, whose proof is a test name or a command. Then the loophole-hunter and a plan reviewer read the draft in parallel, in fresh contexts: at most two hunter rounds and one fix round by the planner, with plain advisories filed as notes outside the digest.

What it writes

  • SPEC.md, a draft ADR, the task files, in reef/features/<slug>/
  • the row's queue edits on your base branch, before the branch exists
  • a review record and the hunter's pass record at the draft's digest

What lets it through

The deterministic check green before the planner returns; a review pass and a hunter pass at the current digest. A hole still open after the second hunter round is yours to rule on at the gate.

Your part

Answer the grill. Only a HALT, two of your own documents contradicting each other, reaches you before the gate.

03 · The gate, last decision 1 of 2

One question: Approve plan <slug> at <digest16>? Your answer is recorded against that exact plan by a hook, from your own words, and only while the deterministic check is green. Because the machines ran first, nothing after your approval voids it: reviewer notes and the ADR status line sit outside the digest, and only a HALT ruling or your own decision edits an approved plan.

What it writes

  • .reef/approvals/<slug>.json, bound to the digest

What lets it through

Your Approve. Say what to change instead and the planner amends, the machines re-check, and you are asked again.

Your part

Read the plan. Approve it, or rule on the holes the hunter left open.

04 · The task graph: /reef-task, or /reef-graph

Every task whose dependencies are done starts at once, each in its own git worktree, on the model its tier names. For each task: an implementer builds it test-first and hands back; a verifier in a fresh context writes its pass or fail rule per criterion before reading the diff, and from the second round judges only what the round changed. A hash of the tree before and after each judge proves it changed nothing. A fresh task runs as one background workflow (graph mode) once this machine's probe has proved the guard reaches workflow agents, and so does a fix round: the implementer gets the failure, the verifier judges what it named. Without that proof it runs in the chat. The loop chooses the mode; you don't. One summary comes back; the merge stays with the orchestrator.

What it writes

  • code and tests, in .reef/worktrees/<id>
  • the judge's report, saved verbatim beside the task; the task's cost in .reef/cost/
  • the task file moves to tasks/done/ on merge

What lets it through

The guard refuses a start outside the ready set, past the retry cap, on the wrong model for the tier, without your approval or the review's pass, or with evidence the orchestrator wrote itself. Three fix rounds per task, then it stops and tells you. A gate past gates.timeout_s is killed.

Your part

None. If you end the session while ready work is idle, Reef says so before the turn ends.

05 · /reef-review

Pushes the feature branch and opens the pull request. Checks that every proof named in the plan still holds on the branch. Runs the loophole-hunter once on the feature's whole diff. Reviews the result against the spec, with one round of fixes under one cap, and drives CI, or your local gate, green. Findings that are not this feature's become found rows in your queue.

What it writes

  • the pull request
  • a green record tied to the exact commit it reviewed

What lets it through

A merge is allowed only against a green record at the PR's current head, and the record is refused without the hunter's pass. Push new code after the record and it has to be earned again.

Your part

By default you merge the feature PR yourself (merge.by: human). Set merge.by: loop and Reef merges it against the green record.

06 · Merge and close decision 2 of 2

The feature lands on your base branch and the row closes in the same step: draft decision records get their final numbers in one sequence, the row moves to the archive with your own words, the journal gets a line with what was measured and what the row cost, and the handoff file is rewritten whole. When a batch is done, a release PR goes from the base branch to the release branch, the release gates run once there, and you merge it.

What it writes

  • numbered ADRs, reef/queue-archive.md, reef/journal.md, HANDOFF.md

What lets it through

A security pass first: a read-only agent audits the release's whole diff against the threat model and the constitution and argues what a scanner cannot reach; its verdict is a record bound to the exact head, and the release PR opens only on a PASS at that head. Then the release gates on the PR: architecture drift, the threat model, a secret scan, your stack's audit. A missing tool counts as a skip, and a skip is not a pass.

Your part

Merge the release. There is no gate on push by design: CI is the wall, and the release merge is always yours; during a delegated night the guard holds it for the morning.

07 · Resume anywhere

Everything Reef knows is on disk. A new session, or one after /clear, reads the head of HANDOFF.md and one status tick, a few hundred tokens, which names the next command and the files behind every id it mentions, and continues every row from its last completed step. The tick never offers a task whose plan lacks your approval or its review; it says awaiting and names what is missing. .reef/status.html is the same picture as a page, refreshed every tick; reef/README.md is the map of the tree.

What it writes

  • HANDOFF.md, rewritten from measured state, including by the guard itself when the session's context runs out
  • .reef/status.html

What lets it through

A context ceiling and a reserve for starting new tasks. Over either, Reef writes the handoff first and then asks you to /clear.

Your part

Run /clear when told. scripts/reef-watch shows what happened while you were away; /reef-doctor says what is wrong and how to fix it.

Who does what

Nine roles. Five of them may not write.

When Reef refuses something, the message names the role it refused. These cards say what each role is allowed to do, so the refusal reads as a rule and not as a bug.

Orchestrator dispatches

Your main Claude Code session. It reads one status tick, starts the ready work, and never writes code or evidence itself; in graph mode it supervises one workflow's summary. It has a context ceiling; before it hits one, it writes the handoff and asks you to /clear.

Planner writes plan files

Drafts or amends one feature's spec, tasks and draft decision record in the feature worktree, from the grill's answers and your footnotes, and returns only when the deterministic check is green. Lean context. Never approves, never reviews, never writes code.

the tier's planner model

Implementer writes code

Builds one task, test-first, in its own worktree. It never commits and never judges its own work. It hands back a short note with a list of claims the verifier will check.

the tier's author model

Verifier read-only

A fresh context that decides its pass or fail rule per criterion before it reads the diff, and from the second round judges only what the round changed. If it cannot open your app in a browser, it says so instead of guessing.

the tier's verifier model

Loophole-hunter read-only

The adversary. On a critical plan before any code, at most two rounds, looking for the way every check stays green while the defect happens; then once per feature on the finished diff before the green record. A blocker fails the round; a smaller finding becomes a found row for you.

the tier's adversary model

Plan-reviewer read-only

Reads the drafted plan, before you see it, for drift between the spec, the decisions, the tasks and the config, and cites what it finds. If two of your own documents contradict each other, it stops and hands the choice to you rather than picking a winner.

the tier's reviewer model

Security read-only

Once per release. Audits the release's diff against the threat model and the constitution, then argues what a scanner cannot reach: untrusted input, the authenticated attacker, the deployment surface. Its verdict is a record at the exact head; the release PR opens only on a PASS.

the security model

Mahmoud read-only

Your proxy, only in a super Reef night: a chief architect and product manager who decides what you would decide, from your profile and your own footnotes, inside the contract you approved before sleeping. Plan approvals, design looks, product questions, holes after the hunter's rounds, triage. Never a hard limit; never the release.

the proxy model, Fable by the owner's choice

Mechanic writes, no claims

The chores a machine can check: a rebase, running the gates, re-taking a measurement, archive edits. It reports exit codes and diffs, never prose.

the cheapest model, sonnet by default
Who runs what

Four tiers. A tier only gets heavier.

The tier decides which model does the work, which model judges it, and how hard they try. You declare a tier on a task; the paths it touches can only move it up: anything touching pii, money or auth is critical, a migration is at least design and needs a Rollback:. A found row whose fix is one file in no risk class is light, with no hunter and no semantic review.

In practice

What to know before you run it.

What Reef needs from your machine, what it will never do to your project, and what each of its stops means and asks of you.

What it needs

macOS or Linux. On Windows, run Claude Code inside WSL2. Native Windows is not supported: the guard needs file locks, a signal timer and process groups that Windows does not have, so inside a Reef project it stops and says so.

Claude Code with the plugin installed from the marketplace.

python3 on the PATH. The guard is Python; without it a dispatch is denied and the Bash check runs degraded.

git with the hooks installed. Hooks are local git config: run make setup after every clone.

gh logged in for the review, record and merge steps. Without it Reef stops with USER ACTION REQUIRED and lists the exact commands it would have run.

What it never does

Overwrite a file you wrote. A differing rendering lands in .reef/proposed/ with a diff; only --accept applies it.

Delete a document. Recalibration archives into reef/archive/<date>/ in one commit that one git revert undoes.

Let a judge write. The verifier, the hunter and the plan-reviewer are read-only by the guard, and a tree hash proves it. Evidence is the agent's: the guard refuses a hand-back or a report the orchestrator wrote itself.

Merge the release. The release PR is yours. There is no push gate by design; CI is the wall.

What you accept

Two human gates, nothing between. You approve a plan at its digest, after the machines have reviewed it, and you merge the release. Nothing after your approval voids it except a HALT you rule on yourself. In a super Reef night you approve one contract instead, your proxy approves plans inside it with every decision recorded as his, and the release still waits for you in the morning.

A row costs real tokens. Planning, review, the task graph and the close are separate sessions, each on the tier's model. On a subscription that is plan usage, not an invoice.

A forge is part of the loop. Review verdicts are records bound to the PR head on GitHub; without a remote the loop hands the merge to you.

Settings

.reef/config.json: the one home for every number.

Every cap, model, branch name and path Reef uses is a key in this one file, written by /reef-init and yours to edit. The table is read from the README at page load. A 0.5 config keeps working: every new key defaults to the old behaviour.

A Claude Code pluginv0.6.0MIT

Run a software project as a graph of gated work. Prove the rules in code.

You write a row in a queue. Reef plans it with you, builds it in parallel in isolated worktrees, has a fresh context verify every task, opens the pull request and closes the row. You approve the plan and you merge the release; everything in between is decided by code, not by a prompt.

  • 1 You decide twice: the plan and the release
  • 2 It never overwrites a file you wrote
  • 3 It resumes from disk after /clear

Start here

Pick your situation. One command each.

The same five rows as the README's quick start, one at a time. Every command below is a Claude Code slash command inside your project.

A new project

/reef-init

One batched question set. The branches and the architecture grill: host, shape, scale, store, auth boundary, one-year non-goals.

What happens. Reef renders one tree from templates adapted to your stack: .reef/config.json (every number, once), AGENTS.md, the constitution, the queue with batch 1 row 1 = the walking skeleton, reef/architecture/architecture.md (intent, C4 L1/L2) with draft ADRs for shape, host, store and auth, the journal, glossary, day-zero, a release-only CI, Dependabot, the git hooks, and every scripts/reef-*.

Idempotent: a second run with nothing changed writes nothing.

An existing project

/reef-init
/reef-assess

Nothing you wrote is overwritten. A differing rendering lands in .reef/proposed/<path> with a diff; apply the ones you choose:

python3 scripts/reef-init.py --accept <path>

What happens. /reef-assess reads how the project works, was written and was pushed, with every claim Observed with a proving path or Inferred. It scores how well a harness can hold the project, then recalibrates its documents into the tree under one batched approval.

Archive, never delete. Undo with one git revert.

A feature to build

/reef-plan <row>→/reef-plan-review→/reef-task <slug>→/reef-review <slug>

Four commands, one human question in the middle of the first: Approve plan <slug> at <digest16>?

What happens. The grill, the spec and the tasks. The deterministic check and the semantic review. The task graph: every ready task at once, each in its own worktree, verified by a fresh judge. Then the PR, the acceptance against SPEC.md, the diff review, the merge and the close.

Each stage is explained in How it works.

A queue of rows

/reef-loop

The outer graph: every ready row through the four feature commands, in parallel where rows do not collide.

What happens. The loop stops only for the owner's decisions, a missing credential, a wrong spec, or a cap. Its questions are batched. State lives on disk, so a new session reads the handoff head and one tick, about 300 tokens, and continues every row from its furthest completed step.

Without a gh-authenticated forge, Reef stops with USER ACTION REQUIRED and says exactly what it would have run.

A fresh clone

make setup

Hooks are local git config and do not survive a clone.

Upgrading from 0.5. Re-run /reef-init. scripts/reef-migrate runs first and adds only keys, keeps gates.test as the alias it is, and writes .reef/version. Every check new in 0.6 warns on content planned under 0.5 and fails only on content planned under 0.6.

The flat tasks/ and docs/ layout keeps working; python3 scripts/reef-migrate --layout moves it in one reviewed commit when you want the tree.

How it works

From a queue row to a merge, seven stages. Click one.

You decide twice in the whole run: you approve the plan and you merge the release. Everything between those two is decided by code on state the agent cannot write. A dark dot marks a stage where you decide.

01 · The queue row you write it

Your backlog is reef/queue.md: one row per feature, with an id, what it depends on, and a batch number. The queue lives in one place, on your base branch in the main checkout, so every session sees the same list.

What you write

A sentence and a batch number. /reef-init seeds row 1 with the walking skeleton, the thinnest end-to-end slice of your project.

What lets it through

The row is in the current batch and every row it depends on is closed.

Your part

Write the rows. Nothing starts until a row is ready.

02 · /reef-plan decision 1 of 2

Reef grills you about the feature, then writes its folder under reef/features/<slug>/: a spec with keyed requirements, one decision record with a diagram, and small vertical-slice tasks whose acceptance criteria cite those keys and whose proof is a test name or a command. Then it asks you the one question.

What it writes

  • SPEC.md, a draft ADR, the task files
  • the rows the grill produced, on your base branch

What lets it through

Approve plan <slug> at <digest16>? Your answer is recorded against that exact plan. If anything in the folder changes afterwards, the approval no longer counts and you are asked again.

Your part

Answer the grill. Read the plan. Approve it, or say what to change.

03 · /reef-plan-review

A deterministic check first: the slug, the keys, every criterion cites a key of its own folder, no more than plan.max_tasks tasks, criteria and sentences under their word caps. Then, for anything heavier than a light task, a reviewer in a fresh context reads the plan for contradictions between the spec, the decisions and the tasks. A design or critical task also gets an adversary asking one question: how can every check be green while the defect happens?

What it writes

  • a stamp over the whole feature folder
  • a pass record for the review, and one for the adversary where it ran

What lets it through

A pass at the plan's current digest. A plan edited after a pass needs a new one; a plan with only light tasks needs the deterministic check alone.

Your part

None, unless the reviewer finds two of your own documents contradicting each other. That is a halt, and it is yours to resolve.

04 · /reef-task, the task graph

Every task whose dependencies are done starts at once, each in its own git worktree, on the model its tier names. For each task: an implementer builds it test-first and hands back; a verifier in a fresh context writes its pass or fail rule per criterion before reading the diff, then judges; the adversary looks again at a finished guard; the task merges into the feature branch. A hash of the tree before and after each judge proves it changed nothing.

What it writes

  • code and tests, in .reef/worktrees/<id>
  • the judge's report, saved verbatim beside the task
  • the task file moves to tasks/done/ on merge

What lets it through

The guard refuses a start outside the ready set, past the retry cap, on the wrong model for the tier, without your approval, or without the review's pass. Three fix rounds per task by default; then it stops and tells you.

Your part

None. If you end the session while ready work is idle, Reef says so before the turn ends.

05 · /reef-review

Pushes the feature branch and opens the pull request. Checks that every proof named in the plan still holds on the branch. Reviews the result against the spec and reviews the diff, with one round of fixes under one cap. Drives CI, or your local gate, green.

What it writes

  • the pull request
  • a green record tied to the exact commit it reviewed

What lets it through

A merge is allowed only against a green record at the PR's current head. Push new code after the record and it has to be earned again.

Your part

By default you merge the feature PR yourself (merge.by: human). Set merge.by: loop and Reef merges it against the green record.

06 · Merge and close decision 2 of 2

The feature lands on your base branch and the row closes in the same step: draft decision records get their final numbers in one sequence, the row moves to the archive with your own words, the journal gets a line written from what was actually measured, and the handoff file is rewritten whole. When a batch is done, a release PR goes from the base branch to the release branch, the release gates run once there, and you merge it.

What it writes

  • numbered ADRs, reef/queue-archive.md, reef/journal.md, HANDOFF.md

What lets it through

The release gates: architecture drift, the threat model, a secret scan, your stack's audit. A missing tool counts as a skip, and a skip is not a pass.

Your part

Merge the release. There is no gate on push by design: CI is the wall, and the release merge is always yours.

07 · Resume anywhere

Everything Reef knows is on disk. A new session, or one after /clear, reads the head of HANDOFF.md and one status tick, a few hundred tokens, and continues every row from its last completed step. The tick never offers a task whose plan lacks your approval; it says awaiting and names the feature instead.

What it writes

  • HANDOFF.md, rewritten from measured state, including by the guard itself when the session's context runs out

What lets it through

A context ceiling and a reserve for starting new tasks. Over either, Reef writes the handoff first and then asks you to /clear.

Your part

Run /clear when told. scripts/reef-watch shows what happened while you were away.

Who does what

Six roles. Three of them may not write.

When Reef refuses something, the message names the role it refused. These cards say what each role is allowed to do, so the refusal reads as a rule and not as a bug.

Orchestrator dispatches

Your main Claude Code session. It reads one status tick, starts the ready work, and never writes code itself. It has a context ceiling; before it hits one, it writes the handoff and asks you to /clear.

Implementer writes code

Builds one task, test-first, in its own worktree. It never commits and never judges its own work. It hands back a short note with a list of claims the verifier will check.

the tier's author model

Verifier read-only

A fresh context that decides its pass or fail rule per criterion before it reads the diff, attacks the last round's fix first, and reports evidence per criterion. If it cannot open your app in a browser, it says so instead of guessing.

the tier's verifier model

Loophole-hunter read-only

The adversary for design and critical work. It reads the plan before any code, and the finished guard after, looking for the way every check stays green while the defect happens. A blocker fails the round; a smaller finding becomes a new queue row for you.

the tier's adversary model

Plan-reviewer read-only

Reads an approved plan for drift between the spec, the decisions, the tasks and the config, and cites what it finds. If two of your own documents contradict each other, it stops and hands the choice to you rather than picking a winner.

the tier's reviewer model

Mechanic writes, no claims

The chores a machine can check: a rebase, running the gates, re-taking a measurement, archive edits. It reports exit codes and diffs, never prose.

the cheapest model, sonnet by default
Who runs what

Four tiers. A tier only gets heavier.

The tier decides which model does the work, which model judges it, and how hard they try. You declare a tier on a task; the paths it touches can only move it up: anything touching pii, money or auth is critical, a migration is at least design and needs a Rollback:.

In practice

What to know before you run it.

What Reef needs from your machine, what it will never do to your project, and what each of its stops means and asks of you.

What it needs

Claude Code with the plugin installed from the marketplace.

python3 on the PATH. The guard is Python; without it a dispatch is denied and the Bash check runs degraded.

git with the hooks installed. Hooks are local git config: run make setup after every clone.

gh logged in for the review, record and merge steps. Without it Reef stops with USER ACTION REQUIRED and lists the exact commands it would have run.

What it never does

Overwrite a file you wrote. A differing rendering lands in .reef/proposed/ with a diff; only --accept applies it.

Delete a document. Recalibration archives into reef/archive/<date>/ in one commit that one git revert undoes.

Let a judge write. The verifier, the hunter and the plan-reviewer are read-only by the guard, and a tree hash proves it.

Merge the release. The release PR is yours. There is no push gate by design; CI is the wall.

What you accept

Two human gates, nothing between. You approve a plan at its digest and you merge the release. Everything else is decided by code on state the agent cannot author.

A row costs real tokens. Planning, review, the task graph and the close are separate sessions, each on the tier's model. On a subscription that is plan usage, not an invoice.

A forge is part of the loop. Review verdicts are records bound to the PR head on GitHub; without a remote the loop hands the merge to you.

Every stop leaves its reason on disk: the tick (python3 scripts/reef-loop.py tick), the handoff, the judge's report saved verbatim beside the task. The measurements behind the defaults live in docs/perf/.

Settings

.reef/config.json: the one home for every number.

Every cap, model, branch name and path Reef uses is a key in this one file, written by /reef-init and yours to edit. The table is read from the README at page load. A 0.5 config keeps working: every new key defaults to the old behaviour.

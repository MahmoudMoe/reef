دليل Reef

إضافة لـ Claude Code تدير مشروعك كـرسم بياني من العمل المحكوم ببوابات: تخطيط، تنفيذ متوازٍ، تحقق مستقل، مراجعة محدودة الجولات، دمج آلي، وإصدار بيدك أنت. الإصدار 0.5.0.

1. ما هو Reef ولماذا

عندما تعمل عدة وكلاء (agents) على مشروع واحد، تظهر ثلاث مشاكل: يكرر الوكيل جولات الإصلاح بلا نهاية، ويراجع الوكيل عمله بنفسه، وتتصادم الوكلاء على نفس الملفات والمنافذ. Reef يحل الثلاثة بـآليات لا بنصائح: سكربتات، حارس (guard) يعترض كل أمر قبل تنفيذه، وخطافات git. وكل آلية تأتي باختبار يُظهرها حمراء عند العيب الذي وُجدت لتمنعه، لأن بوابة لم تُرَ حمراء قط هي زينة.

الرسم البياني (graph)

المهام لها اعتماديات حقيقية (blocked-by). كل مهمة جاهزة تُرسل فورًا، بالتوازي، في نسخة عمل (worktree) خاصة بها.

الحدود كبيانات

عدد الجولات مكتوب في ملف المهمة نفسه، لا في ذاكرة النموذج. الحارس يرفض الإرسال بعد الحد حتى لو «نسي» الوكيل.

الكاتب ≠ المُحقّق

من كتب الكود لا يحكم عليه. المُحقّق سياق جديد، يكتب قاعدة النجاح قبل أن يقرأ الكود، وشجرة الملفات تُقارن قبله وبعده.

مكان واحد لكل حقيقة

كل رقم وقرار يعيش في ملف واحد (.reef/config.json للأرقام) وكل ما عداه يشير إليه. الجملة المكررة هي ما تتعطل عليه المراجعة التالية.

2. كيف تذاكره

بالترتيب، وكل مرحلة تبني على ما قبلها:

  1. المفاهيم (هذا القسم والمسرد أدناه): مهمة، بوابة، حارس، رسم بياني، worktree، طبقة (tier)، سقف الجولات.
  2. التشغيل الأول (القسم 3): مشروع صغير، /reef-init، ثم صف واحد في الطابور حتى الدمج. اقرأ ما كتبه كل أمر.
  3. الاستخدام اليومي (القسم 5): /reef-loop يدير كل شيء؛ أنت تجيب عن أسئلتك فقط، مجمَّعة.
  4. المتقدم (القسمان 6 و7): طبقة design والمرحلة العدائية، الموارد المشتركة، ضبط النماذج والحدود في .reef/config.json.

المسرد

Task (مهمة)
شريحة رأسية واحدة في tasks/NNN-slug.md: النطاق، معايير القبول (كل معيار يسمّي اختباره)، blocked-by، resources، tier. ملف المهمة هو المواصفة (spec).
Gate (بوابة)
فحص حتمي لا يُجادَل: الاختبارات، البناء، فحص الأسرار. gates.fast عند كل commit وgates.full عند التحقق والمراجعة وCI.
Guard (الحارس)
scripts/reef-guard.py: خطاف يعترض كل أمر Bash وكل إرسال وكيل قبل التنفيذ ويرفض ما يخالف القواعد (تجاوز البوابة، مهمة خارج المجموعة الجاهزة، نموذج خطأ، git stash).
Ready set (المجموعة الجاهزة)
المهام التي اكتملت اعتمادياتها ومواردها حرة وعددها تحت graph.parallel. يحسبها scripts/reef-graph.py ready من الملفات على القرص.
Worktree
نسخة عمل git منفصلة لكل مهمة في .reef/worktrees/<id> بفرعها الخاص واعتمادياتها الخاصة.
Tier (الطبقة)
light (مسارات آمنة فقط، صغيرة) / full (الافتراضي) / design (آلية فشلت مرتين، أو خصوصية أو مال أو حارس). الطبقة لا تخف إلا بقرار، وتثقل آليًا من حجم التغيير.
Cap (السقف)
عدد جولات الإصلاح لكل مهمة ولكل بند (caps.attempts). بعده يتوقف العمل ويُسجَّل العائق، ولا جولة رابعة.
Plan stamp (ختم الخطة)
بصمة لمحتوى الخطة بعد مراجعتها؛ أي تعديل على الخطة بعد الموافقة يُبطل الختم فيرفض الحارس الإرسال حتى تُراجَع من جديد.
ADR
سجل قرار معماري: ما قُرّر، لماذا، ما رُفض، وما تكلفته. يُكتب مسودة بلا رقم على الفرع، ويُرقَّم عند الدمج.

3. مشروع جديد: خطوة بخطوة

  1. التثبيت مرة واحدة في Claude Code: 
    /plugin marketplace add MahmoudMoe/reef
/plugin install reef@mahmoudmoe
    وثبّت أيضًا review-toolkit (المراجعون plan-review، code-excellence، code-security في ~/.claude/agents/).
  2. /reef-init داخل المشروع (مستودع git). يسألك سؤالًا واحدًا مجمَّعًا: فرع التكامل وفرع الإصدار (الافتراضي develop → main). ثم يكتشف المكدس (package.json، pyproject.toml، Cargo.toml، go.mod) ويكتب:
    الملفماذا يحمل
    .reef/config.jsonكل إعداد وكل رقم، مرة واحدة: البوابات، السقف، النماذج (roles.*)، graph.parallel، الموارد، الطبقات، حدود الكتابة، الفروع.
    AGENTS.md + CLAUDE.mdتعليمات أي وكيل: الأوامر، التخطيط، كيف يسير العمل، القواعد المقيسة، «Owner decision points». CLAUDE.md سطر واحد يشير إليه.
    .specify/constitution.md8 مواد لا تنكسر، كل مادة تقول ما تمنعه. تغييرها يحتاج ADR ورفع رقم الإصدار.
    docs/queue.mdصف لكل وحدة عمل (id · سطر · depends · source · batch) بلا عمود حالة: الحالة تُقرأ من ملفات المهام. قراراتك حواشٍ بكلماتك.
    docs/adr/README.mdاتفاقية ADR: مسودة draft-<row>-<slug>.md بلا رقم، تُرقَّم عند الدمج.
    docs/journal.md وHANDOFF.mdسجل لكل دمج (الجولات، ما تحقق وكيف، وما لم يتحقق)، وملف تسليم يُعاد كتابته كاملًا نهاية كل جلسة.
    .github/workflows/ci.yml وdependabot.ymlCI على pull requests إلى فرع الإصدار فقط، يشغّل نفس سكربت البوابات المحلي. Dependabot يستهدف فرع التكامل أسبوعيًا مجمَّعًا.
    scripts/reef-* و.githooks/كل آليات Reef نسخة في مشروعك، وخطّاف الـcommit الذي يختبر الـindex.
    docs/day-zero.mdقائمة اليوم صفر: كل سطر أمر أو بوابة، تُعلَّم عندما تخضرّ.
    ثم يثبّت الخطافات (git config core.hooksPath .githooks) ويعمل commit واحدًا chore: reef init.
  3. أكمل اليوم صفر: افتح docs/day-zero.md. الأهم: أمر الاختبار إن لم يُكتشف (gates.full فارغ يعني أن البوابة تفشل بصوت عالٍ حتى تضبطها، لا بوابة وهمية)، وقائمة المسارات الآمنة للطبقة الخفيفة tiers.light.allow، ومواد الدستور مقصوصة على مشروعك.
  4. املأ الطابور بصفوف الدفعة الأولى (Source: planned) قبل أي كود.
  5. /reef-loop: يأخذ أول صف جاهز، يخطط (/reef-plan: أسئلة مركزة ثم شرائح رأسية، كل شريحة تسمّي اختبارها الذي يجب أن يكون أحمر قبل العمل)، سؤال موافقة واحد مجمَّع، مراجعة الخطة (/reef-plan-review)، ثم تنفيذ الرسم (/reef-task) والمراجعة (/reef-review) والدمج إلى develop والإغلاق.
  6. الإصدار: عندما تكتمل الدفعة، يفتح الحلقة pull request من develop إلى main، يعمل CI مرة واحدة، وأنت تدمجه. بعده /clear وتبدأ جلسة جديدة من HANDOFF.md.

4. مشروع موجود: الاعتماد الآمن

نفس الأمر /reef-init، والقاعدة الواحدة لكل ملف:

غير موجود → يُكتب

الملفات التي تنقصك تُولَّد ومتوائمة مع مكدسك.

مطابق → يُتجاوز

التشغيل الثاني بلا تغيير لا يكتب شيئًا (0 written).

مختلف → لا يُستبدل أبدًا

ملفك يبقى كما هو. النسخة المقترحة تُوضع في .reef/proposed/<path> ويُطبع الفرق (diff). تقبل ما تريد: python3 scripts/reef-init.py --accept <path>.

.reef/config.json يُدمَج: المفاتيح الناقصة تُضاف بقيمها الافتراضية، وما ضبطته أنت لا يتغير. .gitignore وMakefile يُضاف إليهما سطر، ولا يُعاد كتابتهما. CLAUDE.md الذي كتبته أنت يبقى لك ولا يُقترح بديل.

الترحيل من 0.3/0.4: لا يتغير شيء في التنفيذ إلا أربع حالات يرفضها الحارس الآن: إرسال مهمة اعتماديتها لم تكتمل، git stash، بوابة مضخوخة في tail، ونموذج غير المضبوط في roles.*. أعد تشغيل /reef-plan-review مرة واحدة (أختام 0.3 تُقرأ كمفقودة). بعد ترقية الإضافة أعد /reef-init: السكربتات المتغيرة تُقترح لا تُستبدل، واقبلها فهي ملك Reef لا ملكك.

5. الاستخدام اليومي

الحلقة رسم بياني

أمر واحد يدير اليوم: /reef-loop. يقرأ الصفوف الجاهزة (scripts/reef-queue.py ready: الدفعة الحالية، المخطط قبل المكتشف)، ويشغّل كل صف لا يتصادم مع غيره بالتوازي، حتى graph.parallel وكيلًا. وداخل كل صف يشغّل /reef-task كل مهمة جاهزة فورًا. ينهي كل رد بسطر واحد: in flight: … / waiting on: ….

كيف يعمل الوكلاء المتوازون

  • كل وكيل تنفيذ في worktree خاص بفرعه task/<id>-<slug>، ويشغّل worktree.setup (مثل npm ci) لنسخته الخاصة من الاعتماديات والكود المولَّد. لا أحد يلمس النسخة المشتركة.
  • الموارد المشتركة تُعلَن في المهمة: resources: [db, port:3000, browser, heavy]. عدد الحاملين في resources.<name>.slots (الافتراضي 1، وheavy اثنان). الأوامر الثقيلة تمر عبر scripts/reef-graph.py lock heavy -- <cmd>.
  • حالة المهمة على القرص فقط (status، attempts، worktree في مقدمة ملف المهمة)، فإعادة التشغيل تعيد حساب الرسم كله: scripts/reef-graph.py status.
  • الدمج بيد المنسّق وحده (كاتب واحد لفرع الميزة)، وبعد التسليم النهائي للوكيل لا عند رؤية تقريره.

متى يسألك ومتى لا

يسألكلا يسألك
بيانات شخصية تخرج من النظام؛ ادعاء تجاري؛ شكل منتجك؛ مال؛ تغيير قاعدة.كل ما عدا ذلك يقرره ويسجله (في ADR أو حاشية).
الموافقة على خطة الدفعة وقرارات طبقة design — في سؤال واحد مجمَّع، كل بند 2–4 خيارات، الموصى به أولًا بعلامة (Recommended) وسطر مقايضة.لا يسأل سؤالًا تلو سؤال. ما لم تجب عنه يأخذ الافتراضي، إلا البيانات الشخصية والادعاءات والتغيير المرئي في منتجك.
عمل التصميم: صفحة معاينة كاملة لكل شاشة قبل أي بناء.داخل البند لا ينتظر موافقة: يتوقف فقط لقرارك، أو بيانات اعتماد ناقصة، أو مواصفة خطأ (يعدّلها ويكمل)، أو السقف.

6. الجودة

مراجعة الخطة

scripts/reef-plan-check.py فحوص حتمية (المعرّفات، الدورات، كل معيار يسمّي اختبارًا، الطبقة تطابق التعقيد، لا عنوان «Open questions») ثم وكيل plan-reviewer يراجع المعنى. النجاح يكتب ختم الخطة.

المُحقّق (verifier)

سياق جديد يكتب RULE AC<n> لكل معيار قبل قراءة الكود، يعيد تشغيل البوابة بنفسه، ويقدم دليلًا لكل معيار. في إعادة التحقق يهاجم إصلاح الجولة السابقة أولًا. أي تعديل منه على الشجرة = فشل تلقائي.

المرحلة العدائية

loophole-hunter يسأل: «كيف يكون كل شيء أخضر والعيب يحدث؟». إلزامي مرتين في طبقة design: على الخطة قبل الكود (الحارس يرفض الإرسال بدون سجلها) وعلى الحارس المكتمل قبل الإغلاق (الـcommit يرفض بدونه). لا يعمل أبدًا على mech.

السقف

caps.attempts جولات لكل مهمة، وسقف واحد للبند كله عبر القبول والمراجعة وCI (ملف rollup واحد). بعد حكم GREEN: commit ادعاءات فقط أو BLOCKER أو صف جديد. لا جولة رابعة.

لماذا يجب أن تُرى البوابة حمراء

بوابة لم تفشل قط أمام العيب الذي وُجدت له قد تكون لا تفحص شيئًا. لذلك لكل آلية في Reef اختبار يُظهرها حمراء أولًا (sh tests/run.sh)، ولكل مهمة اختبار يُسمّى في معيار القبول ويكون أحمر قبل العمل. القاعدة: لا اختبار فاشل = لا مهمة.

7. التوفير: tokens ودقائق CI

ما يفعله Reefما تواصله أنت
النموذج حسب الوظيفة (roles.*): fable للتخطيط ومراجعة الخطة، opus لكتابة الكود والتحقق والمراجعة والهجوم، sonnet للعمل الميكانيكي (rebase، تشغيل البوابات، إعادة القياسات، الأرشفة) ولا يكتب ادعاءً نثريًا. الحارس يرفض نموذجًا غير المضبوط.اترك الأدوار كما هي إلا لسبب مقيس، وغيّرها في .reef/config.json لا في ملفات الوكلاء.
CI على pull requests إلى main فقط، مرة واحدة، مع cancel-in-progress. البوابة المحلية scripts/reef-ci-local.sh تشغّل نفس القائمة وتقرأ كل exit code (2 = شيء تخطّى وليس نجاحًا).لا تدفع إلى develop أثناء CI للإصدار. اجعل gates.fast أقل من دقيقة.
الكتابة أقل: حدود كلمات للمواصفة والتسليم والـprompt (writing.*)، قائمة ادعاءات بدل سرد، مكان واحد لكل حقيقة.اكتب قراراتك في الحواشي بكلماتك، ولا تنسخ رقمًا في مكانين.
منسّق جديد لكل إصدار: HANDOFF.md يُعاد كتابته ثم /clear. سياق المنسّق الطويل كان ~20% من tokens يوم مقيس.اقبل الـ/clear عند نهاية الوحدة، لا في منتصفها.
mech بلا وكيل تحقق (بوابة + اختبار ذهبي)؛ المرحلة العدائية في design فقط.لا تطلب «مراجعة إضافية» على mech؛ ارفع الطبقة إن كان الخطر يستحق.

9. حل المشاكل

reef-guard DENY: … is not in the ready set — blocked-by not done
اعتمادية لم تكتمل. scripts/reef-graph.py status يريك ما ينتظر ماذا. لا تعدّل blocked-by لتمريرها إلا إن كانت الحافة وهمية، وعندها ستحتاج مراجعة خطة.
resource 'db' held by task(s) 4 أو parallel cap 10 reached
انتظر اكتمال الحامل، أو ارفع resources.db.slots / graph.parallel في الإعدادات إن كان الجهاز يحتمل.
plan stamp is stale or missing
الخطة تغيرت بعد مراجعتها (أو لم تُراجَع). شغّل /reef-plan-review في worktree المهمة نفسه. تذكّر أن status وattempts وworktree لا تُبطل الختم، أما resources والنطاق فيُبطلانه.
is at the retry cap / task is blocked
السقف. اقرأ الفشل المسجل (last_failure_sig والسجل)، قرر: أعد التخطيط أو افتح صفًا جديدًا. فك الحظر يدوي وثلاثة حقول: attempts: 0، status: pending، last_failure_sig: "".
must run on roles.author = 'opus'
الإرسال لم يحمل النموذج المضبوط. مرّر model= كما طبعه reef-attempt، أو غيّر الدور في الإعدادات إن كان القرار قرارك.

مهمة design تُغلق بلا مرور الهجوم الثاني على الحارس المكتمل. شغّله وسجّل: … guard <report>.
gate … piped into another command / git stash
اقرأ exit code مباشرة (> out.txt; echo $? أو set -o pipefail). بدل stash: commit على فرع المهمة (البوابة يجب أن تمر) أو worktree آخر.
CI أحمر على pull request الإصدار
اقرأ السجل الفعلي لا اسم الاختبار. سجّل الفشل على rollup الميزة بـscripts/reef-attempt (نفس السقف)، أصلح، وتحقق محليًا بـsh scripts/reef-ci-local.sh --ci قبل الدفع. إن فشل شيء على main ولم يفشل محليًا فالقائمة تختلف: أضفه إلى gates.extra.
reef-ci-local: exit 2
بوابة تخطّت (exit 77). ليست نجاحًا. سمّها بـ--require <name> حتى يصير التخطي فشلًا، أو وفّر ما تحتاجه (قاعدة بيانات محلية مثلًا).
reef-init: PROPOSED <file>
ملف عندك يختلف عن النسخة المولَّدة. اقرأ الفرق المطبوع، ثم --accept لما تريد، وتجاهل الباقي.

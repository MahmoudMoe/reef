# Reef Plan — spec -> approved tasks

**Input:** a raw feature spec (`$ARGUMENTS`: free-form text, a path, or empty — if empty, ask the human for one and stop until they answer).
**Output:** approved task files on a feature branch + optional ADR/glossary additions — exactly what `/reef-task` consumes. Nothing else.

You are the orchestrator: grill → draft (in the feature worktree, by `reef:planner`) → machine review (hunter ‖ plan reviewer, one fix round, one fresh re-check) → the gate, LAST → nothing edits the plan afterwards. The owner touches the plan twice: the grill and the gate (v2, 2026-10-17: three planning sessions without code, every post-gate finding re-ran approval, hunter and review). You do not implement. Read `.reef/config.json` for paths. **Read lean** (measured: planning one row cost 66k tokens of context, a fifth of it reading the checker's source — `docs/design/plan-cost.md`): the tick (`python3 scripts/reef-loop.py tick`), `python3 scripts/reef-queue.py ready`, the head of `AGENTS.md`, the two templates, and `python3 scripts/reef-plan-check.py --rules` ONCE for every rule the checker enforces with this project's numbers. Never read `reef-plan-check.py`, `reef-queue.py` or `reef-approval.py` themselves (the approval is recorded by the hook when the exact question is answered Approve — nothing to look up), never re-implement a lint, never `cat` the whole queue or constitution (the constitution is enforced by code; read it only for a `design`/`critical` task). Write the files, run the check **with `--quiet`** (FAIL/WARN and the summary; the OK lines are context you do not need), fix each FAIL line, repeat — the checker is the oracle.

## 1. Grill
Each question carries a recommended answer. BATCH the independent questions into one AskUserQuestion (up to four per set: data layer, test store, storage, deploy are independent of each other); ask one at a time ONLY when the answer decides whether the next question exists. Budget: at most two sets plus two single questions per row (measured: twelve sequential questions planned one row on 2026-10-16). Only ask what the codebase cannot answer (an Explore agent for a large tree, with its file budget). Stop when scope, edge cases, non-goals, and ADR-worthy decisions are clear.

## 1a. The worktree first
Before any plan text: commit the row's queue edits on `branches.base` in the main checkout and push; `git branch feat/<slug> <base>` and `git worktree add .reef/worktrees/<slug> feat/<slug>`; start the project's `worktree.setup` there in the background. Every plan file is written IN that worktree, so nothing is ever moved and the tick sees the plan from its first line.

## 1b. The feature folder and its SPEC (0.6)
One feature = one queue row = one folder `<paths.features>/<feature-slug>/` (default `reef/features`; a 0.5 project keeps flat `tasks/` until `--layout`). The slug is 2–5 descriptive kebab-case words (`csv-export-for-orders`), never a number or a generic word (`reef-queue.py check` refuses it). Write `SPEC.md` from `${CLAUDE_PLUGIN_ROOT}/templates/spec.md` first: `Row: <id>`, the grill as Q/A, scope, non-goals, `## Already shipped` (grep the repository for the row's nouns, search merged PRs for the row id; `none` is an answer), requirements `FR-n` each tagged `[infra|data|backend|frontend]`, success criteria `SC-n`, owner decisions, `## Architecture impact`. Child specs `specs/<part>.md` (`Parent: FR-n`) only for a big feature; the feature's ADR under `adr/` (one by default, `## Diagram` in Mermaid); tasks under `tasks/`. Nothing else goes in the folder. An existing constitution or spec directory (`.specify/`, `specs/*/spec.md`) is read as input and its keys carried; it is never duplicated.

## 2. Draft (by `reef:planner`, in the worktree)
Split into vertical slices:
- A slice goes ALL THE WAY THROUGH: it touches every layer its behavior needs (schema to output), thin but end-to-end — never "the database part" alone.
- Done means showable: you can run the slice and point at what changed.
- Sized for one clean context: if an agent needs to be reminded mid-way, the slice is too big.
- THE RULE: **no failing test = no task** — every task names the test that would be red before work starts; if you can't, merge or delete the slice.
  - Good: "004 skip-and-warn — red test: bad row currently raises a traceback."
  - Bad: "003 multi-month — grouping already works, task adds a blank line." (This exact padding shipped in the pilot and cost a full round-trip.)
- Wide mechanical refactors are the exception: expand -> migrate-in-batches -> contract, each batch its own task.
Per task, draft the full file from `${CLAUDE_PLUGIN_ROOT}/templates/task.md` (schema: `${CLAUDE_PLUGIN_ROOT}/schemas/task.schema.json`):
- Criteria (0.6 shape): `AC-n (FR-m)` is ONE declarative sentence under 50 words citing the keys it delivers, no test name, no command; the `## Proof` table maps each `AC-n` to its test name or a command that exits 0 iff it holds. Sentences everywhere under 25 words (`writing.sentence_words`). A feature over `plan.max_tasks` (12) is split into dependent queue rows, each with its own folder.
- `touches:` names the risk classes (`pii`, `money`, `auth` force `critical`; `migration` forces at least `design` and a `Rollback:` line in `## Decision`).
- `complexity`: mech = a junior copies an existing example without one question; design = two people would produce materially different solutions.
- `tier`: light (mech only: allowlisted paths, no privacy/money/auth/data path, no migration, no ADR) / full (default) / design (replaces a mechanism that failed twice, or touches privacy, money or a guard — the `loophole-hunter` runs on the plan before code and on the finished guard after). `scripts/reef-plan-check.py` refuses a tier that does not match the complexity.
- `verify`: design -> judge; mech -> gate-only.
- `blocked-by`: only REAL edges — the graph runs every task whose edges are done in parallel, so a decorative edge costs wall-clock, and a missing one lets two tasks collide.
- `resources`: every shared thing the task holds while running — a fixed port (`port:3000`), the database (`db`), the one browser, `heavy` for a full suite or build; the scheduler serialises them (slots in `.reef/config.json`). Name it or two tasks will hold it at once.
- Effort above medium must be argued for in the plan.
Also draft: glossary additions, and at most ONE ADR (Nygard: Status/Context/Decision/Consequences) for the whole feature if it has non-obvious decisions. In a parallel loop, where ADR numbers would collide across branches, write it as `docs/adr/draft-<item>-<slug>.md` and number it at merge — reef-plan-check exempts `draft-*.md` from the "no Proposed ADR" rule (a placeholder or missing Status still fails).

## 3. Explain-back (design tasks)
For each `tier: design` task the HUMAN writes the `## Decision` section in their own words — grill them to sharpen it; never write it for them. For other `design` tasks the orchestrator may draft it, marked `decided by: agent` on its first line, and it joins the question set at the gate. A design task with an empty Decision cannot be dispatched.

## 3.5 Machine review — hunter ‖ plan reviewer, before the owner sees anything
Both at once, fresh contexts, on the same plan-check-green digest: the `loophole-hunter` on every `design`/`critical` task ("how can every check be green while the defect happens?") and the `plan-reviewer` (`/reef-plan-review` steps 1–2b: it records the verdict with `scripts/reef-record plan-review`). Then ONE fix round by `reef:planner`: every BLOCKING finding, every hunter BLOCKER, every advisory marked `WILL BITE`; plain advisories go under `## Reviewer notes` (outside the digest). Then ONE fresh re-check of each that had findings (round 2). `scripts/reef-adversarial <task> plan <report>` records the hunter's PASS and REFUSES a round above `hunter.plan_rounds` (2): a hole still open after round 2 is the owner's decision at the gate (fix as drafted / accept as a found row / drop the task), recorded as a footnote and stamped with `reef-adversarial <task> plan --decided <mark>`, or an AC with a Proof row the code proves. A HALT (two authoritative sources contradicting) stops here and goes to the owner verbatim. `plan.max_acs` (8) bounds a task; the planner splits, never the reviewer.

## 4. HUMAN GATE (one, blocking, batched — and LAST)
Drafting and amending plan files is dispatched to `reef:planner` (fresh, lean: ~7k first-turn context against ~29k for a general-purpose agent; measured 2026-10-17), with the exact files, the footnotes to honour and the worktree path; the planner returns plan-check green. Never a general-purpose agent for plan text. The gate opens only when the machine review has passed and is recorded (`reef-plan-check.py --verify-stamp` shows `review: OK`); the tick names what is missing. Show every task in full (scope, ACs, out-of-scope, resources, tier) with the task list (title / blocked-by / delivers) so the owner judges the granularity here, not in a question of its own; the review's advisories as information, one line each. Write the drafted task files and ADRs to disk first (the plan is what is on disk, not what is in the chat), run `scripts/reef-plan-check.py --feature <slug> --quiet` in the plan's checkout until it prints `0 failed` (the approval hook refuses to record while it fails), then `--digest --feature <slug>` and take the first 16 hex of the digest. ONE question set (AskUserQuestion) holding everything that is the human's, its first question with EXACTLY this text — `Approve plan <slug> at <digest16>?` — and the options `Approve` / `Edit` / `Cancel` (header `Plan`), plus the Design-tier Decisions and where the branch lives (worktree vs current tree), each with a recommended default. Never one question at a time. The approval is a RECORD, not a sentence: the PostToolUse hook (`scripts/reef-approval.py`) writes `.reef/approvals/<slug>.json` only when that exact question is answered `Approve` with the current digest — a timeout, an `Edit`, a hand-written file (the guard denies it) or an edit of the plan afterwards approves nothing, and the guard refuses the first dispatch. After Approve: glossary, ADR (drafts: `draft-<slug>.md`, `Status: Accepted (number at merge)`). **The queue has one home**: every row the grill produced (the roadmap, a split over `plan.max_tasks`, a found row) is committed on `branches.base` in the main checkout and pushed FIRST, as its own commit touching only `paths.queue`; rows and footnotes are written with `scripts/reef-queue.py add-row` / `footnote` (one command each, never inline Python); then create `feat/<slug>` from that head (the spec, tasks and ADR go on the feature branch, never queue rows — `reef-plan-check.py` fails a feature branch whose queue differs from the base's; first contact: rows 2–15 lived only on the feature and the tick never saw them). On Edit: the planner changes the files, the machine review re-runs on what changed (fresh), recompute the digest, ask again. **After Approve nothing edits the plan** but a HALT ruling or an owner decision (both footnoted, both re-stamped with `--decided`); cosmetic changes never happen.

## Re-entry
The tick (`python3 scripts/reef-loop.py tick`) names the row; if its feature folder (or `tasks/NNN-*.md` matching the slug) already exists, do not re-plan from zero — show the existing plan, ask whether to extend, edit, or abandon it. Never overwrite an approved plan silently.

# Reef Plan — spec -> approved tasks

**Input:** a raw feature spec (`$ARGUMENTS`: text, a path, or empty — then ask the human for one and stop until they answer).
**Output:** approved task files on a feature branch + optional ADR/glossary additions — exactly what `/reef-task` consumes. Nothing else.

You are the orchestrator: grill → draft (in the feature worktree, by `reef:planner`) → machine review sized to the path (§3.5) → the gate, LAST → nothing edits the plan afterwards. The owner touches the plan twice: the grill and the gate. You do not implement. Read `.reef/config.json` for paths. **Read lean** (`docs/design/plan-cost.md`): the tick (`python3 scripts/reef-loop.py tick`), `python3 scripts/reef-queue.py ready`, the head of `AGENTS.md`, the two templates, and `python3 scripts/reef-plan-check.py --rules` ONCE (every rule the checker enforces, with this project's numbers); a reviewer's or hunter's report through `python3 scripts/reef-claims.py verdict <report>`. Never read `reef-plan-check.py`, `reef-queue.py` or `reef-approval.py` themselves, never re-implement a lint, never `cat` the whole queue or constitution (the constitution only for a `design`/`critical` task). Write the files, run the check **with `--quiet`**, fix each FAIL line, repeat — the checker is the oracle.

## 1. Grill
Each question carries a recommended answer. BATCH independent questions into one AskUserQuestion (up to four per set); one at a time ONLY when an answer decides whether the next question exists. Budget: at most two sets plus two single questions per row. Ask only what neither the codebase (an Explore agent for a large tree, with its file budget) nor the spec answers. Stop when scope, edge cases, non-goals and ADR-worthy decisions are clear.

## 1a. The worktree first
Before any plan text: commit the row's queue edits on `branches.base` in the main checkout and push; `git branch feat/<slug> <base>`, `git worktree add .reef/worktrees/<slug> feat/<slug>`; then `python3 scripts/reef-setup.py apply .reef/worktrees/<slug>` there in the background — the setup, proven once per change (`state`: unproven → `prove` first; INCOMPLETE → the owner's `worktree.setup`, never a guessed build). Every plan file is written IN that worktree: nothing is ever moved, and the tick sees the plan from its first line.

## 1b. The feature folder and its SPEC (0.6)
One feature = one queue row = one folder `<paths.features>/<feature-slug>/` (default `reef/features`; a 0.5 project keeps flat `tasks/` until `--layout`). The slug is 2–5 descriptive kebab-case words (`csv-export-for-orders`), never a number or a generic word. `SPEC.md` first, from `${CLAUDE_PLUGIN_ROOT}/templates/spec.md`: `Row: <id>`, the grill as Q/A, scope, non-goals, `## Already shipped` (grep the repository for the row's nouns, search merged PRs for the row id; `none` is an answer), requirements `FR-n` tagged `[infra|data|backend|frontend]`, success criteria `SC-n`, owner decisions, `## Architecture impact`. Child specs `specs/<part>.md` (`Parent: FR-n`) only for a big feature; the ADR under `adr/` (one by default, `## Diagram` in Mermaid); tasks under `tasks/`. Nothing else in the folder. An existing constitution or spec directory (`.specify/`, `specs/*/spec.md`) is read as input and its keys carried, never duplicated.

## 2. Draft (by `reef:planner`, in the worktree)
Vertical slices:
- A slice goes ALL THE WAY THROUGH every layer its behaviour needs (schema to output) — thin but end-to-end, never "the database part" alone; done means showable; sized for one clean context.
- THE RULE: **no failing test = no task** — every task names the test that is red before work starts; if you can't, merge or delete the slice. Good: "004 skip-and-warn — red test: bad row currently raises a traceback." Bad: "003 multi-month — grouping already works, task adds a blank line."
- Wide mechanical refactors: expand -> migrate-in-batches -> contract, each batch its own task.
Per task, the full file from `${CLAUDE_PLUGIN_ROOT}/templates/task.md` (schema `${CLAUDE_PLUGIN_ROOT}/schemas/task.schema.json`):
- Criteria (0.6 shape): `AC-n (FR-m)` is ONE declarative sentence under 50 words citing the keys it delivers — no test name, no command, no `file:line` in a criterion, a decision or the scope (lines move; `## Read first` carries them); `## Proof` maps each `AC-n` to its test or a command that exits 0 iff it holds. Sentences under 25 words (`writing.sentence_words`). A feature over `plan.max_tasks` (12) is split into dependent queue rows, each its own folder.
- `touches:` the risk classes (`pii`, `money`, `auth` force `critical`; `migration` forces at least `design` and a `Rollback:` line in `## Decision`).
- `complexity`: mech = a junior copies an existing example without one question; design = two people would produce materially different solutions.
- **Ceremony sized to the row**: a `found` row whose fix is one file in no risk class is ONE task, `mech`, `tier: light` — no hunter, no semantic review. A heavier tier for such a row is argued in `## Decision`, one line; the reviewer never raises a tier the path classes do not force.
- `tier`: light (mech only: allowlisted paths, no privacy/money/auth/data path, no migration, no ADR) / full (default) / design (replaces a mechanism that failed twice, or touches privacy, money or a guard — the hunter runs on the plan before code and on the guard after). `verify`: design -> judge; mech -> gate-only.
- `blocked-by`: only REAL edges (a decorative one costs wall-clock, a missing one lets two tasks collide). `resources`: every shared thing the task holds — `port:3000`, `db`, the browser, `heavy` for a full suite or build — or two tasks hold it at once. Effort above medium is argued in the plan.
Also draft glossary additions and at most ONE ADR (Nygard: Status/Context/Decision/Consequences) for the feature, only if it has non-obvious decisions; in a parallel loop write it as `docs/adr/draft-<item>-<slug>.md`, numbered at merge (`draft-*.md` is exempt from the "no Proposed ADR" rule; a placeholder or missing Status still fails).

## 3. Explain-back (design tasks)
For each `tier: design` task the HUMAN writes `## Decision` in their own words — grill to sharpen it, never write it for them. Other `design` tasks: the orchestrator may draft it, marked `decided by: agent` on its first line, and it joins the gate's question set. A design task with an empty Decision cannot be dispatched.

## 3.5 Machine review — sized to the path, before the owner sees anything
`python3 scripts/reef-tier.py path <the task files>` names the path (v3). **Fast** (every task light or full, no `auth`/`pii`/`money`/`migration` touch): `reef-plan-check.py` alone is the review (`--verify-stamp` says `review: not required`). **Critical**: at once, fresh, on the same green digest — the `loophole-hunter` on every `critical` task (every `design` task too under `hunter.plan_pass: design`) and the `plan-reviewer` (`/reef-plan-review` steps 1–2b; it records the verdict with `${CLAUDE_PLUGIN_ROOT}/scripts/reef-record plan-review`). Then ONE fix round by `reef:planner`: every BLOCKING finding, hunter BLOCKER and `WILL BITE` advisory; plain advisories under `## Reviewer notes` (outside the digest). Then ONE fresh re-check of each that had findings. `scripts/reef-adversarial <task> plan <report>` records the hunter's PASS and REFUSES a round above `hunter.plan_rounds` (2): a hole open after round 2 is the owner's at the gate (fix as drafted / a found row / drop the task), footnoted and stamped `reef-adversarial <task> plan --decided <mark>`, or an AC with a Proof row. The hunter's NEW-ROWs: `reef-queue.py add-row --source found`; NOTED lines: `reef-queue.py note "<the line>" --row <row>` — both on `branches.base`. A HALT (two authoritative sources contradicting) stops here and goes to the owner verbatim. `plan.max_acs` (8) bounds a task; the planner splits, never the reviewer. A plan-pass hunter's prompt carries `pass=plan round=<n>` (this task's plan passes so far); the guard refuses n above `hunter.plan_rounds`.

## 4. HUMAN GATE (one, blocking, batched — and LAST)
Plan text is drafted and amended only by `reef:planner` (fresh, ~7k first-turn context against ~29k for a general-purpose agent), on the model `roles.planner` names (the tier table's `planner` when the prompt carries `REEF-FEATURE: <slug>`) passed as the Agent call's `model` — the guard refuses another, and refuses none — with the exact files, the footnotes to honour and the worktree path; it returns plan-check green. The gate opens only when the review has passed and is recorded (`reef-plan-check.py --verify-stamp`: `review: OK`, or `review: not required` on the fast path). Write the plan to disk first (the plan is what is on disk), run `scripts/reef-plan-check.py --feature <slug> --quiet` in its checkout until `0 failed` (this feature's open tasks are judged on the authoring rules; a finished task under `tasks/done/` keeps the structural checks only; the hook refuses to record while it fails), then `--digest --feature <slug>` (its first 16 hex), then `--summary --feature <slug>`. Show every task in full (scope, ACs, out-of-scope, resources, tier) with the task list (title / blocked-by / delivers) — the owner judges the granularity here, never in a question of its own; the review's advisories one line each. ONE AskUserQuestion set with everything that is the human's: first, EXACTLY `Approve plan <slug> at <digest16>?`, options `Approve` / `Edit` / `Cancel` (header `Plan`), the `Approve` description the `--summary` line VERBATIM, the same line just above the set (never write it yourself); then the Design-tier Decisions and where the branch lives, each with a recommended default. The approval is a RECORD: the PostToolUse hook (`${CLAUDE_PLUGIN_ROOT}/scripts/reef-approval.py`) writes `.reef/approvals/<slug>.json` only when that exact question is answered `Approve` at the current digest — a timeout, an `Edit`, a hand-written file or a later edit approves nothing, and the guard refuses the first dispatch. After Approve: glossary, ADR (`draft-<slug>.md`, `Status: Accepted (number at merge)`). **The queue has one home**: every row the grill produced (roadmap, a split, a found row) is committed on `branches.base` in the main checkout and pushed FIRST, its own commit touching only `paths.queue`, written with `scripts/reef-queue.py add-row` / `footnote` (never inline Python); `feat/<slug>` comes from that head and carries the spec, tasks and ADR, never queue rows (`reef-plan-check.py` fails a feature branch whose queue differs from the base's). On Edit: the planner changes the files, the review re-runs (fresh) on what changed, the digest is recomputed, ask again. **After Approve nothing edits the plan** but a HALT ruling or an owner decision (both footnoted, re-stamped with `--decided`); never a cosmetic change.

## Re-entry
The tick names the row; if its feature folder (or `tasks/NNN-*.md` matching the slug) exists, do not re-plan from zero — show the plan and ask whether to extend, edit, or abandon it. Never overwrite an approved plan silently.

# Reef Plan Review — approved plan -> reviewed plan

Between "the human approved the plan" and "start implementing" there is otherwise no check. This closes it: a blocking script layer, then a bounded agent layer. Read `.reef/config.json` for paths.

0. Work where the plan IS: the feature's worktree (`git worktree list` — the branch under `branches.feature_prefix`, default `feat/<slug>`, usually `.reef/worktrees/<slug>`). From the base branch the plan does not exist yet and the check fails on "no task files" for nothing (first contact: every run tried the base first).
1. Run `scripts/reef-plan-check.py`. Exit 1 = STOP; print its failing lines. It is deterministic; never argue with it, never work around it.
2. Only if it passed: read its last line. `plan-reviewer: none (…)` (every task of the feature is `light`, `tiers.light.roles.plan_reviewer` is `none`; `--needs-agent` exits 3) — the deterministic check alone stamps, stop here. Otherwise spawn the `plan-reviewer` agent (this plugin), fresh context, with the model the script printed (`plan-reviewer: model=…` — the heaviest tier's `plan_reviewer`), the prompt starting with `REEF-FEATURE: <slug>` so the guard resolves the same tier.
2b. The agent's verdict is a RECORD, not a sentence: save its final message VERBATIM to `.reef/ci-local/plan-review-<slug>.md`, then `scripts/reef-record plan-review <slug> PASS --report <that file>` (or `FAIL`). `reef-plan-check.py --verify-stamp` — and so the guard at the first dispatch — requires a PASS at the current digest for any feature with a task above `light`; the deterministic stamp alone never meant the review passed. A plan edited afterwards needs the review again (the record is digest-bound).
3. On BLOCKING findings: the ORCHESTRATOR applies the fix — always in the direction of the approved plan, never against it. Only the brief and `.reef/config.json` are ever corrected; task files and ADRs are authoritative and are never edited to make a finding go away. The fix touches documentation only — never code, never a task file. Then re-run the script, and BEFORE any re-dispatch run `scripts/reef-claims.py blocking-fixed .reef/ci-local/plan-review-<slug>.md <HEAD before your fixes>` — exit 1 names a cited line you left as it was; fix it first (first contact: one ADR line missed cost a full review round and the stop). Then re-dispatch the agent FRESH, as in step 2 — never resume the previous reviewer: a reviewer that re-reads its own verdict defends it (the owner's rule, 2026-10-17). A second round of the same blocking finding is a STOP for the human, not a third attempt.
3b. A HALT (two authoritative sources contradicting each other) is NOT a fix you may apply. Relay it verbatim and stop. An acknowledgment — "ok", "proceed", "looks good" — does not resolve it; only the human naming which source wins AND why does, with the losing side amended in the same change. Dispatching an implementer before that is a violation.
4. On ADVISORY findings: present them to the human as ONE list, one line each, default **leave as is**; only an advisory the reviewer marked `WILL BITE` becomes a question of its own (2–4 options, recommended first). Never act on them alone — they concern the plan itself, which only the human may change. (First full loop, 2026-10-17: 28 advisories over three plans were about to be put to the owner one by one.)
4c. **An approved plan is not edited for anything but a BLOCKING fix, a HALT ruling or an owner decision.** No wording, no ADR status line, no sentence trimming: every edit changes the digest, which voids the approval and the review (first full loop: two approved plans were voided by an ADR status change and a sentence shortening, costing re-approval and a fresh review each). Cosmetic changes wait for the next planned edit or never happen.
4b. Whatever this skill commits (a brief fix, a re-approval's SPEC note) it also PUSHES on the feature branch before returning: the plan is on the forge before any code, and the owner never pushes by hand.
5. Re-entry: state lives in `<tasks>/.plan-review.json` (written by the script on success), not in memory. The stamp is per-worktree (gitignored — the script FAILS if it is tracked) and holds one hash per feature over that feature's task files plus the ADRs; merging the integration branch (other features' tasks, the brief, the glossary, the config) does not stale it. Run the script in the worktree the tasks will be dispatched from.

## Called from reef-task
reef-task runs `scripts/reef-plan-check.py --verify-stamp --feature <slug>` before its first dispatch (the guard runs the same check, in the task file's own worktree, at every implementer dispatch). Non-zero exit = the feature's plan changed since the last review, so this skill runs first and its result is shown to the human before any implementer is spawned.

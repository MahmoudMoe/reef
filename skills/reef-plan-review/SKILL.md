# Reef Plan Review — drafted plan -> reviewed plan, before the gate

v2 (2026-10-17): the review runs BEFORE the owner approves, in parallel with the hunter, so no finding voids an approval. A blocking script layer, then a bounded agent layer. Read `.reef/config.json` for paths.

0. Work where the plan IS: the feature's worktree (`git worktree list` — the branch under `branches.feature_prefix`, default `feat/<slug>`, usually `.reef/worktrees/<slug>`). From the base branch the plan does not exist yet and the check fails on "no task files" for nothing (first contact: every run tried the base first).
1. Run `scripts/reef-plan-check.py --quiet`. Exit 1 = STOP; print its failing lines. It is deterministic; never argue with it, never work around it.
2. Only if it passed: read its last line. `plan-reviewer: none (…)` (every task of the feature is `light`, `tiers.light.roles.plan_reviewer` is `none`; `--needs-agent` exits 3) — the deterministic check alone stamps, stop here. Otherwise spawn the `plan-reviewer` agent (this plugin), fresh context, with the model the script printed (`plan-reviewer: model=…` — the heaviest tier's `plan_reviewer`), the prompt starting with `REEF-FEATURE: <slug>` so the guard resolves the same tier.
2b. The agent's verdict is a RECORD, not a sentence: save its final message VERBATIM to `.reef/ci-local/plan-review-<slug>.md`, then `scripts/reef-record plan-review <slug> PASS --report <that file>` (or `FAIL`). `reef-plan-check.py --verify-stamp` — and so the guard at the first dispatch — requires a PASS at the current digest for any feature with a task above `light`; the deterministic stamp alone never meant the review passed. A plan edited afterwards needs the review again (the record is digest-bound).
3. On BLOCKING findings BEFORE the gate: `reef:planner` applies the fix in the plan files (they are drafts until the owner approves), one round, together with the hunter's BLOCKERs and every `WILL BITE` advisory — within `review.plan_rounds` (default 2: the review, one fix, one re-review; `reef-record` counts the rounds, the guard refuses a dispatch past the cap, the open findings go to the owner as `reef-queue.py ask` questions, and a PASS past the cap records his ruling: `reef-record plan-review <slug> PASS --report <the review> --decided <his footnote's mark>`). AFTER the gate (a HALT ruling, an owner decision) only the brief and `.reef/config.json` are corrected by the orchestrator; task files and ADRs are then authoritative and change only by the owner's footnoted ruling. Then re-run the script, and BEFORE any re-dispatch run `scripts/reef-claims.py blocking-fixed .reef/ci-local/plan-review-<slug>.md <HEAD before your fixes>` — exit 1 names a cited line you left as it was; fix it first (first contact: one ADR line missed cost a full review round and the stop). Then re-dispatch the agent FRESH, as in step 2 — never resume the previous reviewer: a reviewer that re-reads its own verdict defends it (the owner's rule, 2026-10-17). A second round of the same blocking finding is a STOP for the human, not a third attempt.
3b. A HALT (two authoritative sources contradicting each other) is NOT a fix you may apply. Relay it verbatim and stop. An acknowledgment — "ok", "proceed", "looks good" — does not resolve it; only the human naming which source wins AND why does, with the losing side amended in the same change. Dispatching an implementer before that is a violation.
4. On ADVISORY findings: write each as one line under `## Reviewer notes` in the task file it concerns (the section sits right before `## Log`; `reef-plan-check.py` keeps both outside the digest, so the notes void no approval and no review), and show the human the list, one line each, as information. Only an advisory the reviewer marked `WILL BITE` becomes a question of its own (2–4 options, recommended first); never a "fix all now" question. The implementer reads the notes and does or declines each with one reason in its hand-back; the verifier lists an unanswered note as a NIT, never a FAIL. (First full loop, 2026-10-17: 28 advisories applied as plan edits re-ran three hunters, three approvals and three plan reviews — a whole session without code.)
4c. **An approved plan is not edited for anything but a BLOCKING fix, a HALT ruling or an owner decision.** No wording, no sentence trimming: every edit changes the digest, which voids the approval and the review (the ADR `Status:` line and `## Reviewer notes` are the two exceptions the digest ignores) (first full loop: two approved plans were voided by an ADR status change and a sentence shortening, costing re-approval and a fresh review each). Cosmetic changes wait for the next planned edit or never happen.
4b. Whatever this skill commits (a brief fix, a re-approval's SPEC note) it also PUSHES on the feature branch before returning: the plan is on the forge before any code, and the owner never pushes by hand.
5. Re-entry: state lives in `<tasks>/.plan-review.json` (written by the script on success), not in memory. The stamp is per-worktree (gitignored — the script FAILS if it is tracked) and holds one hash per feature over that feature's task files plus the ADRs; merging the integration branch (other features' tasks, the brief, the glossary, the config) does not stale it. Run the script in the worktree the tasks will be dispatched from.

## Called from reef-task
reef-task runs `scripts/reef-plan-check.py --verify-stamp --feature <slug>` before its first dispatch (the guard runs the same check, in the task file's own worktree, at every implementer dispatch). Non-zero exit = the feature's plan changed since the last review, so this skill runs first and its result is shown to the human before any implementer is spawned.

# Reef Loop — the outer graph

**Input:** `docs/queue.md` (`paths.queue`) and the task files. **Output:** rows merged into `branches.base`, closed in the same breath; a release PR into `branches.release` for the HUMAN; a rewritten `HANDOFF.md`.

You are the orchestrator: a MANAGER with a short context. Read `.reef/config.json`. State lives on disk and the ONE read of it is `python3 scripts/reef-loop.py tick` (0.6): rows to plan, tasks to dispatch now, PRs to review, rows to close, in flight, returned-but-unmerged, parked, the stop reason — under 30 lines, computed from the queue, the task files, the worktrees, `.reef/inflight/` and the open PRs. Never run the three status commands plus `git status` plus `gh pr list` by hand. **Read lean**: the tick, the task file in hand, and what the scripts PRINT (`ok`/`REJECTED`/`FAIL` lines) are your inputs; a judge's report is read through `python3 scripts/reef-claims.py verdict <report>` (verdict, blockers, failed criteria, new rows, notes). Never `git diff` code (the judges read it), never read `scripts/reef-*` or `reef-approval.py` source (the checkers are the oracle), never open a full report (its check summarises it). Measured, first contact: a 3-task feature spent 126k of the orchestrator's 150k, most of it on reads the role does not need. `python3 scripts/reef-loop.py start` marks the loop active (the Stop hook then refuses to end a turn that leaves ready work undispatched — once per state); `stop` marks it inactive; `wait "<reason>"` records a chat-side wait (a grill question, a HALT, a USER ACTION REQUIRED, a `/clear` request) so the hook lets the turn end; `clear-wait` when the answer arrives.

## 1. The ready rows — computed
`python3 scripts/reef-queue.py ready` — rows of the current batch whose `Depends` are merged, by the owner's priority label (`p1`, then none or `p2`, then `p3`), then planned before found; a `p1` found row counts as planned. A `check` warning names an issue labelled `reef-row` without an `[id]`: the owner admits it (`reef-queue.py admit <n>`), never you. If it prints only found rows, STOP and escalate: the roadmap is blocked, and a loop quietly doing findings looks identical to a loop choosing them. If `$ARGUMENTS` names a row, that row only. `scripts/reef-queue.py check` must pass first (orphan task files, duplicate ids, word ceilings).

**Questions first, once.** Before planning any row, grill EVERY ready row of the batch in one question set (each with a recommended answer) and footnote the answers verbatim (`reef-queue.py footnote`), so the batch then runs to its gates without asking again. If `.reef/questions.md` exists, ask its questions first as ONE set, footnote the answers, then delete it.

**Headless (`scripts/reef-run.py`, the outer runner).** AskUserQuestion does not exist there: keep every row moving that does not need the owner, append each owner question to `.reef/questions.md` (`- row <id>: <question> — recommended: <answer>`), at the ceiling hand off with `reef-loop.py wait "/clear requested …"` (the runner starts the next session), and when no row can move without the owner, `reef-loop.py wait "owner: <what>"` and end. Plan approvals stay interactive (the hook records only an answered question).

## 2. Per ready row, in parallel where they do not collide (up to `graph.parallel`)
Rows that share a module collide: plan them ONE AT A TIME (a HALT between two plans voids both approvals and both reviews — first full loop, 2026-10-17, rows 2 and 11 on the bill store). Rows in different modules may plan in parallel; the owner's questions are still one set.
1. `/reef-plan <row>`: worktree first, the planner drafts there, hunter ‖ plan reviewer (one fix round, one fresh re-check, `hunter.plan_rounds` enforced by `reef-adversarial`), THEN one batched gate for everything that is the human's (approval at the digest, Design-tier Decisions, a hunter hole open after round 2). The gate is last: after Approve only a HALT ruling edits the plan. `/reef-plan-review` alone only after such a ruling.
2. The task graph, every ready task at once, each in its worktree, caps per task — in the mode the tick names: `dispatch (graph): …` → `/reef-graph` (generate, ONE Workflow call, settle; `graph.mode: auto` chooses it when this machine's probe recorded GATE OK), `verify (graph): …` → the same (a hand-back, judged without an implementer), `dispatch (chat): …` → `/reef-task` (no gate, or `graph.mode: chat`). A fix round runs in the graph too: the implementer gets the failure, the verifier the `rejudge:` line. The merge is yours in both.
3. `/reef-review <feature>`: PR into `branches.base`; acceptance; diff review (`code-excellence` as a subagent when the review-toolkit is installed — its prompt states "the owner owns this scope — run its declared gates"); `scripts/reef-ci-local.sh` as the feature gate (`ci.feature_gate: local`); one rollup under one cap; after GREEN only a claims-only commit. `merge.by: loop` → merge with `--delete-branch`, only after the agent's FINAL hand-back.
4. **Close in the same breath**, on `branches.base`, as its single writer: `scripts/reef-queue.py adr-number` (drafts numbered), the row and its footnotes moved to `docs/queue-archive.md` (`queue.home: issues`: `scripts/reef-queue.py close <id> --pr <n>`; footnotes stay in the queue file), `scripts/reef-queue.py journal <slug>` (each task's journal block, from its task file), then the journal entry (rounds used, what was verified and how, what was not, and the row's cost: `python3 scripts/reef-cost.py growth --feature <slug>` — share and planning share across sessions), the worktrees removed. Hold pushes to `branches.base` while a release PR's CI runs.
5. Back to step 1: the merge may have unblocked rows. End every reply with ONE last line `in flight: … / waiting on: … / next: <the one command the owner runs — the tick's `next command:`>`; the Stop hook refuses a reply without it while the loop is active.

## 3. Stops — and only these
A decision that is the owner's (personal data leaving the system, a commercial claim, the look of his product, money, a rule change) — collected, not asked one at a time; a missing credential or quota; a spec found wrong (amend, push, resume); the cap (`caps.attempts`) on an item — blocker into the journal, the item parked, the rest of the loop continues; **the context ceiling** (`caps.context_tokens`, measured by the guard on every dispatch from the session transcript — the denial says "checkpoint, then /clear"); **no progress** (`loop.no_progress_ticks` identical ticks with nothing in flight parks the loop: USER ACTION REQUIRED); **a budget** (`caps.feature_tokens` / `caps.batch_tokens` over the ceiling parks the feature or batch); **release ready**. Every stop is recorded as a wait or a stop reason (`reef-loop.py wait`), never only said. **The batch is frozen**: a finding goes to the next batch as a `found` row unless it loses a person's data, exposes a secret or personal data in merged code, or breaks the core journey — then it enters with its ground in `Admitted`, journaled.

## 4. The owner's questions — batched, with defaults
At fixed points only — the end of a merge wave, before a release, or when one blocks the critical path — ONE AskUserQuestion (on issues it also carries `reef-queue.py triage` at every batch boundary and whenever the tick names untriaged found rows; each answer is `set-priority`, `drop-row`, `demote` or a merge footnote): each question 2–4 options, the recommended one first with "(Recommended)", one line of trade-off each. An unanswered question takes its default, except personal data, a commercial claim or a visible change to his product. His words go verbatim into a queue footnote. Queue edits are COMMANDS, never inline Python: `scripts/reef-queue.py footnote "<his words>" [--row ID]` (numbered across queue and archive, dated), `add-row --item … --depends … --source planned|found [--batch N] [--admitted <ground>]`, `set-depends ID "<ids>"`, `set-batch ID N`, `drop-row ID --reason "…"`; then `reef-queue.py check`. **Rule 7 is a command**: when the tick prints `stale found (rule 7): N`, run `scripts/reef-queue.py triage` and put its rows to the owner as ONE question at the batch boundary (promote with a reason → `set-batch` + footnote; merge into a design row → footnote on that row + `drop-row`; delete → `drop-row --reason`); never carry a found row past two batches unasked, never answer for him. (First full loop: hand-written heredocs for these were 15% of the session.) Design work: a full previewable page of every screen before any build.

## 5. Release
When the batch's rows are merged: **the security pass** — dispatch `reef:security` (model `roles.security`) on `git diff <branches.release>...<branches.base>` with a scratchpad report path; `cp` its report to `.reef/ci-local/security-<sha12>.md`, then `scripts/reef-record security <PASS|FAIL> --report <that copy>` (the record carries the agent's own VERDICT line; a BLOCKER is a FAIL and goes back as a task, its HIGHs go to the owner in the release question set; each `NEW-ROW` becomes a found row, `reef-queue.py add-row --source found` — a security finding is never a note). Then `gh pr create --base <branches.release> --head <branches.base>` — the guard refuses it without a PASS security record at that head, so a base that moved since the pass is audited again; CI runs there, once (`gates.release` run there and only there); **the HUMAN merges**, and on issues closes the batch's milestone, so the next batch is current. **Checkpoint and clear (0.6):** at the end of every merge wave, and whenever the context ceiling fires, `python3 scripts/reef-handoff --write` renders `HANDOFF.md` whole from the tick, the journal tail and the open questions (no prose from memory), `reef-loop.py wait "/clear requested"`, and the human is asked to `/clear` — a fresh orchestrator starts from the handoff head and the tick alone (a long orchestrator context was ~20% of a measured day's tokens; the baseline is `docs/perf/baseline-2026-10-16.md`).

## Re-entry
The handoff head (`HANDOFF.md`, first 40 lines) and `python3 scripts/reef-loop.py tick` — nothing else is read at start (the SessionStart hook injects exactly these, under `writing.session_start_tokens`). Continue every row from its furthest completed step; never re-plan a row with task files, never re-create a rollup, never reset a cap. One session holds a project's loop: the guard refuses a second while the holder acted in the last 30 minutes; `wait` and `stop` hand it over, and only the owner runs `python3 scripts/reef-loop.py unlock`.

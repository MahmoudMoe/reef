# Reef Loop — the outer graph

**Input:** `docs/queue.md` (`paths.queue`) and the task files. **Output:** rows merged into `branches.base` and closed in the same breath; a release PR into `branches.release` for the HUMAN; a rewritten `HANDOFF.md`.

You are the orchestrator: a MANAGER with a short context. Read `.reef/config.json`. State lives on disk; the ONE read of it is `python3 scripts/reef-loop.py tick` — rows to plan, tasks to dispatch, PRs to review, rows to close, in flight, returned-but-unmerged, parked, the stop reason. A row's one next step: `python3 scripts/reef-row.py next <row>` (plan → approval → build → evidence → review → merge → close); you run the step it names. **Read lean**: the tick, the task file in hand, what the scripts PRINT; a judge's report through `python3 scripts/reef-claims.py verdict <report>`. Never `git diff` code, never read `scripts/reef-*` source, never open a full report. `reef-loop.py start` marks the loop active (the Stop hook then refuses a turn that leaves ready work undispatched); `stop` marks it inactive; `wait "<reason>"` records a chat-side wait (a grill question, a HALT, a USER ACTION REQUIRED, a `/clear` request) so the turn may end; `clear-wait` when the answer arrives.

## 1. The ready rows — computed
`scripts/reef-queue.py check` must pass first (orphan task files, duplicate ids, word ceilings). `python3 scripts/reef-queue.py ready` — the current batch's rows whose `Depends` are merged, by priority label (`p1`, then none or `p2`, then `p3`), planned before found (a `p1` found row counts as planned). **Finish before starting** (v3): the tick plans a new row only while fewer than `loop.rows_in_flight` (default 2) are between plan and close. Only found rows ready: STOP and escalate — the roadmap is blocked. `$ARGUMENTS` names a row: that row only. An issue labelled `reef-row` without an `[id]` is admitted by the owner (`reef-queue.py admit <n>`), never you.

**Questions first, once.** Before planning any row, grill EVERY ready row of the batch in one question set (each with a recommended answer) and footnote the answers verbatim (`reef-queue.py footnote`). If `.reef/questions.md` exists, ask its questions first as ONE set; record each answer with the command its line names — `reef-queue.py answered <#> "<answer>"` for a line with `#<issue>`, the footnote on its row otherwise.

**Headless (`scripts/reef-run.py`, the runner).** No AskUserQuestion there: keep every row moving that does not need the owner; file each owner question with `python3 scripts/reef-queue.py ask "<question>" --row <id> --recommended "<answer>"`; at the ceiling `reef-loop.py wait "/clear requested …"` (the runner starts the next session); when no row can move, `reef-loop.py wait "owner: <what>"` and end. Plan approvals stay interactive. The owner answers from a terminal — `reef approve <row>`, `reef answer <row> "<text>"`, or `reef`, the screen, one key per wait — and the runner resumes by itself.

## 2. Per ready row (up to `graph.parallel`)
Rows that share a module plan ONE AT A TIME (a HALT between two plans voids both approvals and reviews); rows in different modules may plan in parallel; the questions are still one set.
1. `/reef-plan <row>`: worktree first, the planner drafts there, the machine review sized to the path, THEN one batched gate for everything that is the human's. After Approve only a HALT ruling edits the plan; `/reef-plan-review` alone only after such a ruling.
2. The build: under graph mode a whole row in ONE Workflow — `python3 scripts/reef-graph-run.py row <row>` (`/reef-graph` "The row"), then `settle`, then the one bare `gh pr merge` it names. Otherwise every ready task at once, in the mode the tick names: `dispatch (graph):` and `verify (graph):` → `/reef-graph`; `dispatch (chat):` → `/reef-task`. A fix round runs in the same mode (the implementer gets the failure, the verifier the `rejudge:` line). The merge is yours in every mode.
3. `/reef-review <feature>`: PR into `branches.base`, ONE review (`reef:acceptance`), `scripts/reef-ci-local.sh` as the feature gate under `ci.feature_gate: local`; one rollup under one cap; after GREEN only a claims-only commit. `merge.by: loop` (the default under `ci.feature_gate: ci` when the base is not the release branch) → `scripts/reef-merge-base` in the feature worktree, push, merge with `--delete-branch` only after the agent's FINAL hand-back and a green gate on the merged head (the guard refuses a head without the base's tip or green evidence).
4. **Close in the same breath**, on `branches.base`, as its single writer: `scripts/reef-queue.py adr-number`; the row and its footnotes to `docs/queue-archive.md` (`queue.home: issues`: `scripts/reef-queue.py close <id> --pr <n>`, the footnotes stay in the queue file); `scripts/reef-queue.py journal <slug>`; the journal entry (rounds used, what was verified and how, what was not, the cost from `python3 scripts/reef-cost.py growth --feature <slug>`); the worktrees removed. Hold pushes to `branches.base` while a release PR's CI runs.
5. Back to step 1. End every reply with ONE last line `in flight: … / waiting on: … / next: <the tick's next command: line, verbatim>`; the Stop hook refuses a reply without it while the loop is active.

## 3. Stops — and only these
An owner's decision (personal data leaving the system, a commercial claim, the look of his product, money, a rule change) — collected, not asked one at a time; a missing credential or quota; a spec found wrong (amend, push, resume); the cap (`caps.attempts`) on an item — blocker to the journal, the item parked, the loop continues; **the context ceiling** (`caps.context_tokens`; the guard's denial says "checkpoint, then /clear"); **no progress** (`loop.no_progress_ticks` identical ticks, nothing in flight: USER ACTION REQUIRED); **a budget** (`caps.feature_tokens` / `caps.batch_tokens` parks the feature or batch); **release ready**. Every stop is recorded (`reef-loop.py wait`), never only said. **The batch is frozen**: a finding is a `found` row of the next batch unless it loses a person's data, exposes a secret or personal data in merged code, or breaks the core journey — then it enters now with its ground in `Admitted`, journaled.

## 4. The owner's questions — batched, with defaults
**The proxy by day first (v3).** With `reef/proxy.md` approved (`python3 scripts/reef-run.py contract --day` prints `Approve proxy by day at <digest16>?` — ONE AskUserQuestion, once; an edit to `reef/proxy.md` or `reef/owner.md` voids it), a question of a kind its `Decides:` line names (`process` and `wording` by default; `plan`, `question`, `hole`, `triage` under `reef autopilot`) goes first to `reef:mahmoud` (model `roles.proxy`) with the row and a report path under THIS session's scratchpad (the one home the guard allows a report); `cp` his report to `.reef/ci-local/report-mahmoud-day-<row>.md`, then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/reef-approval.py --proxy --day --kind <kind> --row <row> --report <that copy>` — it writes his footnote itself (the guard refuses one typed by hand) or says `WAIT`, and only then the owner. Product, money, data, look, security and the release are never his.

**Mahmoud's `CHALLENGE` and `RESEARCH` lines — once, never a loop.** A `CHALLENGE <plan> — <wrong> — <instead>` on a plan: `cp` the report to `.reef/ci-local/report-mahmoud-challenge-<row>.md`, then `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/reef-approval.py --proxy --challenge --row <row> --report <that copy>`. Exit 0 records it (once per row, on disk) and you carry it: the plan amended as an Edit through `/reef-plan` (the machine review re-runs, the digest recomputed), then Mahmoud asked once more on the amended plan. An exit 3 is the second challenge on the row — the owner's (`reef-queue.py ask`, his words as the question). A `RESEARCH <question>`: one `Explore` agent (read-only, never `general-purpose`) on exactly his question, about the world, never this repository's code or secrets; its result goes back to him once. Neither reaches a review or a hole.

At fixed points only — the end of a merge wave, before a release, or when one blocks the critical path — ONE AskUserQuestion (on issues it carries `reef-queue.py triage` at every batch boundary and whenever the tick names untriaged found rows; each answer is `set-priority`, `drop-row`, `demote` or a merge footnote): 2–4 options each, the recommended first with "(Recommended)", one line of trade-off each. An unanswered question takes its default, except personal data, a commercial claim or a visible change to his product. His words go verbatim into a footnote. Queue edits are COMMANDS, never inline Python: `scripts/reef-queue.py footnote "<his words>" [--row ID]`, `add-row --item … --depends … --source planned|found [--batch N] [--admitted <ground>]`, `set-depends ID "<ids>"`, `set-batch ID N`, `drop-row ID --reason "…"`; then `reef-queue.py check`. **Rule 7**: when the tick prints `stale found (rule 7): N`, run `scripts/reef-queue.py triage` and put its rows to the owner as ONE question at the batch boundary (promote with a reason → `set-batch` + footnote; merge into a design row → footnote there + `drop-row`; delete → `drop-row --reason`); never carry a found row past two batches unasked, never answer for him. Design work: a full previewable page of every screen before any build.

## 5. Release
**Long work is the runner's.** Headless (`REEF_RUNNER=1`), a command that may run past two minutes — the full gate, `reef-converge`, a CI wait — is a runner job: `python3 scripts/reef-run.py job <name> -- <command…>` (letters, digits, dashes), then `python3 scripts/reef-loop.py wait "job: <name> — <what it proves>"` and END the turn. Never a background shell in a headless session: it keeps the runner waiting on it. The runner resumes this conversation with `JOBS DONE … <name> rc=<rc>` when the job ends within five minutes and the context is under `caps.context_warn`, else the next session starts with it; the log is `.reef/run/jobs/<name>.log`. With the owner at the keyboard, background shells are fine.

When the batch's rows are merged: **the security pass** — dispatch `reef:security` (model `roles.security`) on `git diff <branches.release>...<branches.base>` with a scratchpad report path; `cp` its report to `.reef/ci-local/security-<sha12>.md`, then `${CLAUDE_PLUGIN_ROOT}/scripts/reef-record security <PASS|FAIL> --report <that copy>` (a BLOCKER is a FAIL and goes back as a task; its HIGHs go to the owner in the release question set; each `NEW-ROW` becomes a found row, `reef-queue.py add-row --source found` — a security finding is never a note). Then `gh pr create --base <branches.release> --head <branches.base>` (the guard refuses it without a PASS security record at that head); `gates.release` runs there and only there; **the HUMAN merges** and, on issues, closes the batch's milestone. **Checkpoint and clear:** at the end of every merge wave and whenever the context ceiling fires, `reef-loop.py wait "/clear requested"` — every wait renders `HANDOFF.md` from the tick, the journal tail and the open questions (the guard refuses a hand-written one) — and the human is asked to `/clear`.

## Re-entry
The handoff head (`HANDOFF.md`, first 40 lines) and `python3 scripts/reef-loop.py tick` — nothing else at start. Continue every row from its furthest completed step; never re-plan a row with task files, never re-create a rollup, never reset a cap. One session holds a project's loop: the guard refuses a second while the holder acted in the last 30 minutes; `wait` and `stop` hand it over; only the owner runs `python3 scripts/reef-loop.py unlock`.

# Reef Loop — the outer graph

**Input:** `docs/queue.md` (`paths.queue`) and the task files. **Output:** rows merged into `branches.base`, closed in the same breath; a release PR into `branches.release` for the HUMAN; a rewritten `HANDOFF.md`.

You are the orchestrator: a MANAGER with a short context. Read `.reef/config.json`. State lives on disk and the ONE read of it is `python3 scripts/reef-loop.py tick` (0.6): rows to plan, tasks to dispatch now, PRs to review, rows to close, in flight, returned-but-unmerged, parked, the stop reason — under 30 lines, computed from the queue, the task files, the worktrees, `.reef/inflight/` and the open PRs. A row's state and its one next step: `python3 scripts/reef-row.py next <row>` (plan → approval → build → evidence → review → merge → close, from disk; you run the step it names). **Read lean**: the tick, the task file in hand, and what the scripts PRINT (`ok`/`REJECTED`/`FAIL` lines) are your inputs; a judge's report is read through `python3 scripts/reef-claims.py verdict <report>` (verdict, blockers, failed criteria, new rows, notes). Never `git diff` code (the judges read it), never read `scripts/reef-*` or `reef-approval.py` source (the checkers are the oracle), never open a full report (its check summarises it). `python3 scripts/reef-loop.py start` marks the loop active (the Stop hook then refuses to end a turn that leaves ready work undispatched — once per state); `stop` marks it inactive; `wait "<reason>"` records a chat-side wait (a grill question, a HALT, a USER ACTION REQUIRED, a `/clear` request) so the hook lets the turn end; `clear-wait` when the answer arrives.

## 1. The ready rows — computed
`python3 scripts/reef-queue.py ready` — rows of the current batch whose `Depends` are merged, by the owner's priority label (`p1`, then none or `p2`, then `p3`), then planned before found; a `p1` found row counts as planned. **Finish before starting** (v3): the tick plans a new row only while fewer than `loop.rows_in_flight` (default 2) rows are between plan and close; the rest wait, named on its `rows to plan` line. A `check` warning names an issue labelled `reef-row` without an `[id]`: the owner admits it (`reef-queue.py admit <n>`), never you. If it prints only found rows, STOP and escalate: the roadmap is blocked. If `$ARGUMENTS` names a row, that row only. `scripts/reef-queue.py check` must pass first (orphan task files, duplicate ids, word ceilings).

**Questions first, once.** Before planning any row, grill EVERY ready row of the batch in one question set (each with a recommended answer) and footnote the answers verbatim (`reef-queue.py footnote`), so the batch then runs to its gates without asking again. If `.reef/questions.md` exists, ask its questions first as ONE set, footnote the answers, then delete it.

**Headless (`scripts/reef-run.py`, the outer runner).** AskUserQuestion does not exist there: keep every row moving that does not need the owner, file each owner question with `python3 scripts/reef-queue.py ask "<question>" --row <id> --recommended "<answer>"` (its line in `.reef/questions.md`; on issues also an issue assigned to the owner, closed by `reef-queue.py answered <#n> "<answer>"` once answered), at the ceiling hand off with `reef-loop.py wait "/clear requested …"` (the runner starts the next session), and when no row can move without the owner, `reef-loop.py wait "owner: <what>"` and end. Plan approvals stay interactive (the hook records only an answered question).

## 2. Per ready row, in parallel where they do not collide (up to `graph.parallel`)
Rows that share a module collide: plan them ONE AT A TIME (a HALT between two plans voids both approvals and both reviews). Rows in different modules may plan in parallel; the owner's questions are still one set.
1. `/reef-plan <row>`: worktree first, the planner drafts there, the machine review sized to the path (hunter ‖ plan reviewer on the critical path, the check alone on the fast path), THEN one batched gate for everything that is the human's (approval at the digest, Design-tier Decisions, a hunter hole open after round 2). The gate is last: after Approve only a HALT ruling edits the plan. `/reef-plan-review` alone only after such a ruling.
2. The build: under graph mode a whole row in ONE Workflow — `python3 scripts/reef-graph-run.py row <row>` (its tasks in order, each closed in place, then the evidence, the PR and the one review; `/reef-graph` "The row"), then `settle`, then the one bare `gh pr merge` it names. Otherwise the task graph, every ready task at once, in the mode the tick names: `dispatch (graph): …` → `/reef-graph` (generate, ONE Workflow call, settle), `verify (graph): …` → the same (a hand-back, judged without an implementer), `dispatch (chat): …` → `/reef-task` (no gate, or `graph.mode: chat`). A fix round runs in the graph too: the implementer gets the failure, the verifier the `rejudge:` line. The merge is yours in every mode.
3. `/reef-review <feature>`: PR into `branches.base`; ONE review (`reef:acceptance`: the spec, the diff, the evidence); `scripts/reef-ci-local.sh` as the feature gate (`ci.feature_gate: local`); one rollup under one cap; after GREEN only a claims-only commit. `merge.by: loop` (the default under `ci.feature_gate: ci` when the base is not the release branch) → `scripts/reef-merge-base` in the feature worktree, push, and merge with `--delete-branch` only after the agent's FINAL hand-back and a green gate on the merged head — the guard refuses a head without the base's tip or without green evidence.
4. **Close in the same breath**, on `branches.base`, as its single writer: `scripts/reef-queue.py adr-number` (drafts numbered), the row and its footnotes moved to `docs/queue-archive.md` (`queue.home: issues`: `scripts/reef-queue.py close <id> --pr <n>`; footnotes stay in the queue file), `scripts/reef-queue.py journal <slug>` (each task's journal block, from its task file), then the journal entry (rounds used, what was verified and how, what was not, and the row's cost: `python3 scripts/reef-cost.py growth --feature <slug>` — share and planning share across sessions), the worktrees removed. Hold pushes to `branches.base` while a release PR's CI runs.
5. Back to step 1: the merge may have unblocked rows. End every reply with ONE last line `in flight: … / waiting on: … / next: <the one command the owner runs — the tick's `next command:`>`; the Stop hook refuses a reply without it while the loop is active.

## 3. Stops — and only these
A decision that is the owner's (personal data leaving the system, a commercial claim, the look of his product, money, a rule change) — collected, not asked one at a time; a missing credential or quota; a spec found wrong (amend, push, resume); the cap (`caps.attempts`) on an item — blocker into the journal, the item parked, the rest of the loop continues; **the context ceiling** (`caps.context_tokens`, measured by the guard on every dispatch from the session transcript — the denial says "checkpoint, then /clear"); **no progress** (`loop.no_progress_ticks` identical ticks with nothing in flight parks the loop: USER ACTION REQUIRED); **a budget** (`caps.feature_tokens` / `caps.batch_tokens` over the ceiling parks the feature or batch); **release ready**. Every stop is recorded as a wait or a stop reason (`reef-loop.py wait`), never only said. **The batch is frozen**: a finding goes to the next batch as a `found` row unless it loses a person's data, exposes a secret or personal data in merged code, or breaks the core journey — then it enters with its ground in `Admitted`, journaled.

## 4. The owner's questions — batched, with defaults
**The proxy by day first (v3).** With `reef/proxy.md` approved (`python3 scripts/reef-run.py contract --day` prints `Approve proxy by day at <digest16>?` — ONE AskUserQuestion, once; an edit to `reef/proxy.md` or `reef/owner.md` voids it), a question of kind `process` or `wording` goes to `reef:mahmoud` (model `roles.proxy`) before the owner: the question, the row and a scratchpad report path; `cp` his report to `.reef/ci-local/report-mahmoud-day-<row>.md`, then `python3 scripts/reef-approval.py --proxy --day --kind <kind> --row <row> --report <that copy>` — it writes his footnote `Mahmoud (proxy, day <date>, <kind>): …` itself (the guard refuses one typed by hand) or says `WAIT`, and only then the owner. Product, money, data, look, security and the release are never his.
At fixed points only — the end of a merge wave, before a release, or when one blocks the critical path — ONE AskUserQuestion (on issues it also carries `reef-queue.py triage` at every batch boundary and whenever the tick names untriaged found rows; each answer is `set-priority`, `drop-row`, `demote` or a merge footnote): each question 2–4 options, the recommended one first with "(Recommended)", one line of trade-off each. An unanswered question takes its default, except personal data, a commercial claim or a visible change to his product. His words go verbatim into a queue footnote. Queue edits are COMMANDS, never inline Python: `scripts/reef-queue.py footnote "<his words>" [--row ID]`, `add-row --item … --depends … --source planned|found [--batch N] [--admitted <ground>]`, `set-depends ID "<ids>"`, `set-batch ID N`, `drop-row ID --reason "…"`; then `reef-queue.py check`. **Rule 7 is a command**: when the tick prints `stale found (rule 7): N`, run `scripts/reef-queue.py triage` and put its rows to the owner as ONE question at the batch boundary (promote with a reason → `set-batch` + footnote; merge into a design row → footnote on that row + `drop-row`; delete → `drop-row --reason`); never carry a found row past two batches unasked, never answer for him. Design work: a full previewable page of every screen before any build.

## 5. Release
When the batch's rows are merged: **the security pass** — dispatch `reef:security` (model `roles.security`) on `git diff <branches.release>...<branches.base>` with a scratchpad report path; `cp` its report to `.reef/ci-local/security-<sha12>.md`, then `scripts/reef-record security <PASS|FAIL> --report <that copy>` (the record carries the agent's own VERDICT line; a BLOCKER is a FAIL and goes back as a task, its HIGHs go to the owner in the release question set; each `NEW-ROW` becomes a found row, `reef-queue.py add-row --source found` — a security finding is never a note). Then `gh pr create --base <branches.release> --head <branches.base>` (the guard refuses it without a PASS security record at that head); CI runs there, once (`gates.release` run there and only there); **the HUMAN merges**, and on issues closes the batch's milestone, so the next batch is current. **Checkpoint and clear (0.6):** at the end of every merge wave, and whenever the context ceiling fires, `reef-loop.py wait "/clear requested"` — every wait renders `HANDOFF.md` whole from the tick, the journal tail and the open questions (never from memory: the guard refuses a hand-written one) — and the human is asked to `/clear`; a fresh orchestrator starts from the handoff head and the tick alone.

## Re-entry
The handoff head (`HANDOFF.md`, first 40 lines) and `python3 scripts/reef-loop.py tick` — nothing else is read at start. Continue every row from its furthest completed step; never re-plan a row with task files, never re-create a rollup, never reset a cap. One session holds a project's loop: the guard refuses a second while the holder acted in the last 30 minutes; `wait` and `stop` hand it over, and only the owner runs `python3 scripts/reef-loop.py unlock`.

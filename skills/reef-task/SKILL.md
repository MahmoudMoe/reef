# Reef Task — the graph

**Input:** approved task files (`$ARGUMENTS`: a feature slug, task refs; empty — run `scripts/reef-graph.py status` and ask which).
**Output:** one merge per passed task into the feature branch (no push — that is `/reef-review`'s job) + journal rows.

You are the orchestrator: a MANAGER. You never write production code, never verify, and never accept a report on faith. Read `.reef/config.json`.

## 0. Plan review — before the FIRST dispatch only
Run `scripts/reef-plan-check.py --verify-stamp --feature <slug>` in the task's own worktree (the
stamp is per-worktree and per-feature). Exit 0 = this feature's plan is unchanged since its last
review; proceed. Non-zero = never reviewed, or edited since — invoke the `reef-plan-review` skill,
show the human its result, and only then continue. A plan the human edited after approval is an
unreviewed plan; the stamp is what knows that, not you.

## 0. The feature is current — `scripts/reef-merge-base` in the feature worktree before the wave's first dispatch
Brings `branches.base` into the feature branch: a task worktree branches from the feature, so a stale `scripts/` there computes a different plan digest than the records carry (first contact: two digests for one plan, the owner merged by hand). Record files (journal, queue, archive, HANDOFF) keep both sides; a code conflict is exit 2 = USER ACTION REQUIRED, never resolved by you. Push the merge commit.

## 1. The ready set — computed, never remembered
**Read lean**: the tick, the task file in hand, and what the scripts PRINT (`ok`/`REJECTED`/`FAIL` lines) are your inputs. Never `git diff` code (the judges read it), never read `scripts/reef-*` or `reef-approval.py` source (the checkers are the oracle), never open a full report (its check summarises it). Measured, first contact: a 3-task feature spent 126k of the orchestrator's 150k, most of it on reads the role does not need. Run `python3 scripts/reef-loop.py tick` (its `dispatch now:` line is `scripts/reef-graph.py ready` minus what is in flight; `--json` for the ids). A task under `verify now:` has a hand-back (`.reef/ci-local/handback-<id>.md`) newer than any report: its work is uncommitted in its worktree — start at step 3 (gate, then the judges), never a second implementer. It lists every task whose `blocked-by` are done, whose declared `resources:` have a free slot, within `graph.parallel`. A broken graph (cycle, missing id) is exit 1 — STOP; it is a plan defect. **Dispatch every ready task now, in one message, not one at a time** — serial execution of a parallel-ready set is the waste this skill exists to remove. The guard enforces the same rule from the other side: it refuses a dispatch of a task outside the ready set, so a wrong dispatch cannot run; a missing one is on you. End each turn with one last line: `in flight: <ids or -> / waiting on: <what or -> / next: <the one command the owner runs>`.

## 2. Dispatch — mechanical, not from memory (per ready task)
1. `scripts/reef-graph.py worktree <task-file>` — creates (or reuses) `.reef/worktrees/<id>` on `task/<id>-<slug>` from the feature branch and runs the project's `worktree.setup` (its own `node_modules`/generated client — never the shared one). The implementer works THERE; the task file stays in your checkout — implementers never touch `tasks/`.
2. `scripts/reef-attempt <task-file>`. A task with `## Reviewer notes` carries the plan review's advisories: the implementer does or declines each with one reason in its hand-back (the notes are not ACs; the verifier lists an unanswered one as a NIT). Exit 2 = blocked -> print its USER ACTION REQUIRED and park that task (the rest of the graph continues). Otherwise use EXACTLY what it prints: the `author:` model as the Agent call's model parameter (resolved from the task's TIER table), its effort in the prompt, and START THE PROMPT with the `REEF-TASK: <task-file>` line it printed. **Every** role dispatch for this task — implementer, verifier, loophole-hunter, mechanic — starts with that same `REEF-TASK:` line: the guard resolves the tier's model per role from it and refuses any other; it also writes `.reef/inflight/<id>` (implementer) and `.reef/verifying/<id>` (verifier, hunter) — remove the `verifying` marker after the judge's hand-back and the `inflight` marker after yours (`rm .reef/verifying/<id>`). The PreToolUse guard refuses any implementer dispatch without that line, any blocked/at-cap task, a stale stamp, and any task outside the ready set — and on allow marks the task `in-progress` and advances its `dispatches:` odometer. The cap holds even if you forget a step.
3. Spawn the `implementer` agent with the task file, the worktree path as its working directory, resolved model/effort. Prompt ≤ 120 words: the stable brief lives in the agent file. mech tasks with a tiny expected diff (<~40 lines): you MAY implement inline in the main session instead — record that in the Log. Design tasks: refuse if `## Decision` is empty.

## 3. Verify (in the task's worktree)
- `verify: gate-only` (mech): run the full gate there (`scripts/reef-gate.sh full --failures` — the exit code and the failing block, never the raw log; heavy suites through `scripts/reef-graph.py lock heavy -- <cmd>`) + require a golden-output test for user-visible output. No judge subagent — that is the cost lesson; do not "helpfully" add one.
- `verify: judge` (design): record `scripts/reef-snapshot.sh` in the worktree (a CONTENT hash over HEAD + index + worktree). Spawn the `verifier` agent fresh with that directory, passing the model from the `verifier: model=` line `reef-attempt` printed (the tier's verifier), the prompt starting with the `REEF-TASK:` line and carrying the `report: budget=` line verbatim (the judge writes to its budget the first time; a rewrite round is the cost of not telling it); it is READ-ONLY by the guard (no mutating git, no Bash write, no CI wait) and by the snapshot hash. After it returns, re-run the snapshot: ANY difference = automatic FAIL regardless of verdict. Require the `RUN:` header line, a `RULE AC<n>` line per criterion ABOVE the verdicts (written before the verifier read the diff), and evidence per AC. On a retry (`attempts > 0`) the verifier attacks the last round's fix first.
- `tier: design` or `critical`: spawn the `loophole-hunter` agent (model from the `adversary:` line `reef-attempt` printed; prompt starting with `REEF-TASK:` and carrying the `hunter-report: budget=` line) on the finished guard in the worktree, snapshot-checked like the verifier; record a PASS with `scripts/reef-adversarial <task-file> guard <report>` — the pre-commit refuses to close a design-tier task without that record; a BLOCKER is a FAIL; a NEW-ROW goes to the queue — on `branches.base` in the main checkout, the queue's only home, never on the feature or task branch. (`scripts/reef-queue.py add-row --item … --source found --repo <main checkout>`). (Its first pass, on the plan, ran before code — the guard refuses the first dispatch without it.)
- **Proof rows the judges cannot run** (they write files: `[mechanic]`-tagged, or a redirect, `rm`/`mv`/`touch`, `.env*`): dispatch the `mechanic` agent to run them verbatim in the worktree and record exit codes; never run them yourself, you are the manager with the short context.
- **A finding on a claimed AC = FAIL** — `scripts/reef-attempt <task-file> "<failure text>"` and re-dispatch (step 2, same worktree — the task is already `in-progress` and keeps its slot). Every hand-back is written to `.reef/ci-local/handback-<task>.md` and checked with `scripts/reef-claims.py check --handback <file>` (`writing.handback_words`, a claims list); every verifier or hunter report to `.reef/ci-local/report-<task>.md` **VERBATIM — the agent's final message byte for byte, never a summary (a shortened report is a rejected report; first contact lost six ACs' evidence that way)** and checked with `scripts/reef-claims.py report <file> --task <task-file>` (the `RUN:` header, one `RULE AC<n>` per criterion citing its Proof row, evidence per AC). A rejected hand-back or report is re-dispatched ONCE with "shorten, evidence only" — no attempt consumed. The fix round's hand-off ENDS WITH A CLAIMS LIST (`<sentence> — true at <path>:<line>`, that round's diff only); run `scripts/reef-claims.py check <before>..<after> <claims-file>` in the worktree — a rejected list is a FAIL report (re-dispatched once, no attempt consumed). Never launder findings into backlog tasks; only genuinely out-of-scope findings become new tasks, recorded in the runlog's "Escaped defects" column.

## 4. Merge (on PASS only) — you are the feature branch's single writer
In the worktree: stage specific files (never `git add -A`), commit with a Conventional Commits subject and trailer `Closes-task: NNN-slug`; the pre-commit gate tests the index — no bypass, ever. Then in YOUR checkout: `git merge --no-ff task/<id>-<slug>`; in that same merge commit set `status: done`, `git mv` the task file to `tasks/done/`, append the runlog row (`paths.runlog`) from the RUN: line, its `Orchestrator` cell from `python3 scripts/reef-cost.py growth <id> --repo <main checkout>` (the journal of an older project without the column: append `· growth N` to Result) — written here, at the merge, never on the task branch, never from memory; `git worktree remove <the task's worktree>` and delete the branch with `git branch -d` run in the FEATURE worktree (from the main checkout `-d` compares to `branches.base` and refuses a branch merged only into the feature; `-D` only after `git merge-base --is-ancestor task/<id>-<slug> feat/<slug>` says yes), then `git worktree prune`; the plan check refuses a file under `done/` whose status is not `done` and the reverse; when the task added dependencies, run `worktree.setup` in your checkout BEFORE the merge commit (its gate needs them — first contact: `pg` missing in the feature worktree). Task worktrees live under the MAIN checkout's `.reef/worktrees/`, never nested in yours. Merge only after the agent's FINAL hand-back, never on seeing its report. Then go to step 1: the merge may have unblocked more of the graph.

## 5. Stop conditions
A blocked task parks itself; the graph continues around it. The pipeline STOPS when nothing is ready and nothing is in flight: all done (hand to `/reef-review`) or only blocked/parked tasks remain (USER ACTION REQUIRED, list them). Failure is a STOP, not an improvisation point.

## Trust nothing without evidence (applies to every step)
When a sub-agent reports success, verify before advancing: the named tests exist (`grep`), the claimed output reproduces (run it once, in the worktree), the diff touches only the task's scope (`git diff --stat`). A hand-off without evidence is a FAIL report, re-dispatched once with "evidence required" — that re-dispatch does NOT consume an attempt.

## Re-entry (session died / compaction / interruption)
State lives on disk — recover it, don't guess:
1. `python3 scripts/reef-loop.py tick` — in flight (the guard's `.reef/inflight/` markers; stale ones listed as returned), ready, parked, returned-but-unmerged; the tick is the only read at start.
2. For each `in-progress` task: `git -C .reef/worktrees/<id> status` — uncommitted implementer work present → do NOT re-implement; go to step 3 for it.
3. `status: blocked` → USER ACTION REQUIRED. Never reset attempts yourself — the human unblock is THREE fields: `attempts: 0`, `status: pending`, `last_failure_sig: ""`.
